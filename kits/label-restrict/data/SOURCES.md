# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every label extract and every proposed
application from a fixed seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild
and there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `label-restrict-2026-08-22-52cases` |
| licence | **MIT** — this repository's own licence |
| cases | 52, in `data/corpus/*.txt`, 56,006 bytes |
| gold | 52 rows in `data/gold.jsonl`, each carrying both answers |
| check set | `data/checks.json` — **written for this kit**, see the warning below |
| products / registrations / actives / fields / notes | invented identifiers, coined product and active-substance names, invented field references and invented agronomist notes, with no link to any real product, manufacturer, registration, holding or adviser |

## ⚠︎ The check set is illustrative and is NOT an authority

**`data/checks.json` was authored for this kit.** It reproduces **no** real product label, **no**
manufacturer's use instructions, **no** national or regional registration, **no** approved-use
database and **no** regulator's guidance. Nothing in it was copied from, derived from or checked
against any such document, because none was consulted.

It is a small, deliberately readable construction whose only job is to make the *decision shape*
measurable: eight restrictions read off a label, compared against one proposed application, in a
fixed precedence order, so that both the verdict and the restriction that decided it are checkable
facts rather than opinions. Several of its simplifications are visibly not how a real label works —
most obviously that eight restrictions can be walked in one order for every product and every crop,
when a real label carries crop-specific rates, crop-specific intervals, growth-stage windows and
conditions that apply only in certain situations.

**The real authority for any application is the approved label for that product in that territory,
the conditions of its registration, and a qualified adviser.** This kit proposes a verdict with its
reasoning, names the restriction that decided it, and names what it could not determine. It never
authorises an application, and nothing in it writes, dispatches, releases or clears anything. That
sentence is on the kit's own UI, above the answer, and not only here.

**Every product name, registration number and active substance in this corpus is coined.**
`Corvenal 250 SC`, `Trelmara 400 EC`, `korvamide`, `REG-2019-04417` and everything like them name no
real product, no real chemistry and no real register, and the registration-number format resembles
no real one. **Every crop name is an ordinary generic crop noun** — maize, winter wheat, field
lettuce, sugar beet. No manufacturer, distributor, assurance scheme, adviser or regulator is named
anywhere in this kit.

⚑ The product name, the registration number and the active substance all live in the
`Product and Registration` section, which `src/select.py` maps to **no field** and which is
therefore never sent to the model at all. That is deliberate twice over: it is the visible part of
what selection saves, and it means the model is never shown a made-up active substance and asked to
reason about it — a question it could only answer wrongly.

⚠︎ **One artefact of the generation order is visible if you read the cases closely**: the product
name is drawn *after* the label's prohibited tank-mix list, so a handful of cases prohibit mixing
with a product that happens to be the case's own. It is harmless — the section naming the product
is never sent, and the tank-mix check compares the proposal's partner against the list — but it is
a construction artefact rather than a realistic label, and it is recorded here rather than quietly
left for a reader to find.

## Why an invented set of cases, when real labels exist

**Because a real label and a real spray plan are not something this repo can publish either.** The
label is a manufacturer's copyrighted document approved by a national authority; the proposal names
a real holding, a real parcel, a real crop destined for a real buyer and a named adviser's own
remark. There is no public corpus of (label, proposed application, correct verdict, correct
deciding restriction) pairs, for the same reason there is no public corpus of bank statements or
certificates of analysis.

Generating it also makes both labels mechanical: gold's `verdict` and gold's `deciding_restriction`
are the walk of `data/checks.json` over the same twenty values the page itself states, never
somebody's reading of the agronomist's note.

## The mechanic: one call per case, twenty-two fields

Each case states a field reference, the product and its registration, eight label restrictions, an
eight-line proposed application, the previous season's application count, whether the application
has already been made, and the agronomist's own free-text remark. The model extracts twenty-two
fields — everything except the product identity, which no field maps to and which is therefore
never sent — including the two it has to decide: the verdict and the restriction that decided it.
See `src/prompt.py`.

**The check set is sent with every call.** A precedence walk is a rule, and a model cannot walk a
rule it has never been shown. `src/prompt.py::check_block()` renders `data/checks.json` into the
prompt rather than restating it in prose, so the model's instructions and the gold labels cannot
drift apart about the same eight checks. Measured on the worked example: 1,201 of 3,558 input
tokens (34%) are the check set.

## The rule, and the two things a reader gets wrong about it

```
verdict(label, proposal):
    walk the eight checks in order, and STOP at the first that fires
      a check that is NOT APPLICABLE is skipped, and it passes
      a check whose value is NOT STATED  -> insufficient_information, naming that check
      a breach of checks 1-5 (crop, tank mix, rate, season count, buffer)
                                         -> outside_label,  naming that check
      a breach of checks 6-8 (re-treatment, pre-harvest, re-entry intervals)
                                         -> wait_required,  naming that check
      nothing fires                      -> within_label,   deciding restriction `none`
```

**HARD BEATS TIMING, and that is the whole reason checks 1-5 come first.** A case that breaches both
a hard restriction and an interval is `outside_label`. Answering `wait_required` there tells a
grower to wait a fortnight before making an application that must not be made at all, which is the
most expensive wrong answer this kit can produce.

**EVERY LIMIT IS INCLUSIVE EXCEPT ONE.** A rate exactly on the maximum is inside the label; a
pre-harvest interval of 35 days is satisfied by exactly 35 days to harvest; a 5 m buffer is
satisfied by exactly 5 m. But `maximum applications per season` is a **total**, so a proposal made
when that many have already been applied would be the next one and is over it.

Five things are stated to the model in full, because each is a reading a careful person still falls
into — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **the season maximum is a total, not a ceiling you may sit on** | `maximum applications per season: 3` with three already made reads as "at the limit, therefore inside", and is the opposite | **5 cases** |
| **an inclusive limit looks exactly like a breach** | a case whose rate, buffer and pre-harvest interval all sit *exactly* on their limits is entirely inside the label | **6 cases** |
| **a near-neighbour crop is not the crop** | the permitted list carries winter wheat and the proposal is for spring wheat, or field lettuce against protected lettuce. Matching on the head noun clears an application the label does not | **5 cases** |
| **hard beats timing** | a hard restriction and an interval both breached; the answer is `outside_label` and not "wait" | **4 cases** |
| **the re-entry interval is the only restriction in hours** | its numbers (24, 48) sit in the same range as the day counts above it, and this corpus deliberately puts the same numeral in both places | **5 cases** |

The rule lives in one function — `src/checks.py::decide()` — used to write gold, rendered to the
model by `src/prompt.py` out of the same JSON file, re-run over the model's own reply by
`evals/judge.py`, and served verbatim to the UI. Four readers, one definition, so the corpus, the
prompt, the diagnostic and the page cannot drift about what a verdict means or about which
restriction decided it.

## The planted ambiguity: the verdict is a walk, and the note disagrees with it

`N_AMBIGUOUS = 21` puts an agronomist's note from the wrong register on exactly 40.4% of cases:

- a proposal that must not be made, carrying a relaxed note — "Routine programme for this block.
  Nothing about it concerns me.";
- a proposal entirely inside the label, carrying a note that reads like a problem — "Spray records
  for this parcel are disputed and are under manual audit this week."

Gold's `verdict` is **never** derived from the note. It is the walk, run over the same values the
page itself states.

## The second decoy: last season's applications

Every case states how many applications were made in the **previous** season. The label maximum is
per season, so that number is part of no check. On every one of the `within_label` cases it is set
so that **adding** it to this season's count crosses the maximum — and **26 cases in total** change
answer if a reader adds the two. A decoy nobody could act on is not a decoy; this one is one line of
arithmetic away from a wrong refusal.

⚑ **That 26 is re-walked, not estimated, and the difference matters.** The obvious proxy — `made <
max AND made + previous > max` — counts 25, and it is wrong in both directions. It over-counts by 4,
on cases where an earlier hard check already fires and the season count is never reached. And it
under-counts by 5, on cases where no application has been made this season at all: adding a previous
season's applications there does not cross the maximum, it **un-skips the re-treatment check** —
whose not-applicable clause is exactly `applications_made_this_season is 0` — and a check that stops
being not-applicable becomes unreadable, because `days since the last application` is null on those
cases. The decoy has a second mechanism nobody designed, and only running the rule found it.
`evals/check_labels.py` runs it.

`evals/check_labels.py` re-runs the walk over every gold row before a run is allowed to spend, and
fails if any label — verdict or deciding restriction — disagrees with its own values. It separately
asserts a floor on each of the five hard cases above, that all three confusable intervals carry at
least three cases each (or a right-verdict-wrong-reason error could not be told from noise), and
that every note template classifies to the register it was written as, against the free floor's own
keyword list, before anything may spend. A sibling kit earlier in this series shipped a keyword that
fired on a negation inside a relaxed note and mis-registered four records for days; that check is
written into this kit's gate from the start rather than found live.

## The composition is exact, then shuffled — not drawn per case

Each of the thirteen buckets is a fixed **count**, shuffled by the seeded RNG, and every constructor
is asserted against the check set at build time — on **both** answers, not just the verdict. A
constructor that quietly stops producing its own bucket is exactly the defect an exact composition
exists to prevent.

| | |
|---|---|
| `within_label` | 14 |
| — inside with room to spare | 8 |
| — every value exactly on an inclusive limit | 6 |
| `outside_label` | 18 |
| — a near-neighbour crop, not on the label | 4 |
| — one rung above the maximum rate | 3 |
| — the season allowance already used in full | 4 |
| — a prohibited tank-mix partner | 2 |
| — nearer the water than the buffer allows | 1 |
| — a hard restriction **and** an interval, both breached | 4 |
| `wait_required` | 14 |
| — the re-treatment interval has not elapsed | 5 |
| — harvest is nearer than the pre-harvest interval | 5 |
| — re-entry planned inside the re-entry interval (hours) | 4 |
| `insufficient_information` | 6 |
| — the label extract does not state the deciding interval | 4 |
| — the proposal does not state days to harvest | 2 |
| agronomist note from the contradicting register | 21 (40.4%) |
| already applied | 23 |
| not inside the label **and** already applied — the hold flag | 16 |

Note the deciding-restriction spread that falls out of it: `pre_harvest_interval` 9,
`min_retreatment_interval` 6, `permitted_crops` 5, `max_applications_per_season` 5,
`re_entry_interval` 5, `max_rate_per_application` 4, `buffer_to_water` 2, `tank_mix_prohibited` 2,
`none` 14. **Twenty of the fifty-two cases turn on one of the three confusable intervals**, which is
what makes "right verdict, wrong restriction" a measurable failure here rather than a hypothetical
one.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises a hold when the verdict is anything other than `within_label`
**and** the application has already been made. A planned application can simply be changed before
the sprayer goes out — a different product, a lower rate, a fortnight later, or not at all — and
nothing has happened yet. The same verdict on an application already made means the product is on
the crop, which is the case somebody has to deal with today. `insufficient_information` counts here
too — treating an unknown as a pass is the one thing a label check must never do.

⚠︎ **This is the kit's own simplification, not anybody's real procedure.** No manufacturer's
guidance, assurance-scheme rule or regulation was consulted, and none is reproduced. A real holding
weighs which restriction was breached and by how much, whether the crop is destined for food or
feed, what the buyer's own assurance scheme requires, and who has authority to decide.

## What it cannot tell you

⚠︎ **This kit reads and proposes only — it never authorises an application, never releases or
withdraws anything and never contacts anybody.** `verdict` and `deciding_restriction` are extracted
fields and `needs_hold` is a routing signal; nothing here disposes of anything.

⚠︎ **A run that scores perfectly has agreed with `data/checks.json`, which is a much smaller claim
than being right about a real label.** The graders measure whether the run walked the shipped check
set. They cannot measure whether the check set is correct, because it is this kit's own
construction.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real label
carries confusions this one does not attempt — a rate that differs by crop and by growth stage, a
pre-harvest interval that differs by crop on the same label, a maximum expressed as total product
per hectare per season rather than per application, growth-stage windows, resistance-management
limits on a whole mode-of-action group rather than one product, buffer distances that vary with
nozzle and boom height, conditions that apply only on certain soils or slopes, and a label whose
approval has been amended since the copy in front of you was printed. A model that clears this
corpus has cleared what this corpus tests, not every way a label check can go wrong.
