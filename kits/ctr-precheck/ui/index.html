Pre-check a draft currency-transaction filing against the log it came from

One QC pack — a draft filing beside the cage transaction log it was prepared from — one model call, a field table, and a defect list produced afterwards in pure code from the extracted values. The check re-adds the log under the rulebook’s own aggregation window, links the patron records that are one person, compares each transaction code against the log’s own, checks the identification block, and asks whether the threshold was ever crossed at all. The preparer’s note sits on the same page and decides nothing.

This pre-checks a draft. It files nothing and it clears nothing. It proposes a worklist with the rulebook’s own reasoning attached and names what it could not determine; a qualified person decides what is submitted. Nothing here lodges, transmits, approves, signs or closes anything. The rulebook shipped with this kit is invented and is not an authority — the threshold, the aggregation window, the staleness horizon, the identification elements and the transaction codes were all written for this kit, and they reproduce no real regulation, form or filing instruction. Amounts are in CU, an invented unit that is not a currency. Replace the whole rulebook with your own programme’s before you decide anything real by it.

Two lists, and the page shows both on purpose. The Defects row is the rulebook run in pure code over the values the reply extracted; the Reply’s own list row is what the reply itself said. They almost always agree, and the case where they do not is the one worth seeing — it means the reply’s own numbers do not support its own conclusion. That comparison uses no gold at all, so it is the one check here you can still run on packs nobody has labelled. It is blind to a reply that mis-adds the log and then reasons correctly from the wrong total, which on this kit is the commonest way to be wrong.

The recompute flag is a business condition, not a check on the model: needs_recompute fires when the defect list contains anything that changes what would be filed — missed_aggregation, window_misapplied, identity_split, threshold_not_crossed or insufficient_information. A missing identification element or a mis-coded transaction is corrected in place and the numbers still stand; an under-reported total goes back to the preparer and everything downstream of it is done again. insufficient_information counts here too — treating a record nobody can compute a total from as though it were clean is the one thing a pre-check must never do. This split is the kit’s own invention, not any compliance programme’s triage policy — no programme, filing instruction or supervisory guidance was consulted, and none is reproduced.
