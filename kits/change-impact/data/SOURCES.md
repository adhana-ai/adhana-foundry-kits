# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every record and every message from a
fixed seed (`SEED = 20260818`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260818` |
| licence | **MIT** — this repository's own licence |
| vendors | 10, in `data/vendors.json` |
| records | 43 open records in `data/records.jsonl` |
| messages | 70 in `data/messages.jsonl` |
| gold | 70 rows in `data/gold.jsonl` — match, change type, extracted value and computed impact per message |
| formats | json (vendors), jsonl (records, messages, gold) |

## Why an invented vendor and an invented record, when real ones exist

**Because a real one cannot be published at all.** A real change request names a real
counterparty, a real committed price and a real ship date — exactly the material a business will
not let leave the building. There is no public corpus of paired (correspondence, structured
record, adjudicated impact) triples for the same reason no public corpus of production alerts or
signed supplier agreements exists: the interesting cases are exactly the ones nobody can publish.

**Nothing in here refers to a real company.** Vendor names, SKUs, product descriptions and message
phrasing are invented; no message here states a real commercial term.

## The job is generic; the flavour is not

This kit's actual job — extract a requested change from unstructured correspondence, match it to
the specific record it modifies, compute the downstream impact of accepting it — applies to any
structured record and any correspondence that proposes changing one. This corpus happens to
flavour "record" as a purchase-order line and "correspondence" as a vendor email requesting an
expedite, a delay, a cancellation, a quantity change or a price change, because that is one
concrete, checkable instance of the job, not because the job is about purchase orders. Point
`tools/build_corpus.py` at your own record shape and your own correspondence and the pipeline —
`src/block.py`, `src/prompt.py`, `src/impact.py` — does not change.

## Three match outcomes, planted and counted

Every message has a KNOWN gold match — a specific `record_id`, or `NONE` when the vendor's product
in question genuinely has no open record (10 of 70 messages, one per vendor, planted on purpose,
not a coin flip: every vendor's third product carries zero open records at all).

Of the 60 messages with a real gold match, 31 name or imply the record unambiguously (an explicit
`REC-#####` reference, or the vendor+product combination resolves to exactly one open record) and
29 are genuinely ambiguous: more than one open record shares the vendor and the product, and the
message carries no explicit record reference. Those 29 each state the CURRENT value of a field the
requested change does not touch — a quantity, or a ship date — specifically so a reader (model or
person) can tell the candidates apart. A checker that ignores that clue cannot solve these; one
that reads it can.

## Five change types, each with a deterministic impact formula

`src/impact.py` computes the cost impact and the ship-date impact from the record and the
extracted change alone — never asserted by a model, never hand-typed into gold. See its own header
for all five formulas. The one worth stating here: **a `delay` costs nothing unless it pushes
shipment past a live promotion's end date, in which case the WHOLE promotion value is lost** — not
a per-day fee, a cliff. 45% of records in this corpus carry a live promotion window, so that cliff
is a real, exercised case and not a hypothetical.

## What blocking and the free floor cannot tell you

⚠︎ **The free floor (`evals/baseline.py`) reuses the SAME blocking code the real pipeline runs**
(`src/block.py`), so the two are compared on identical candidate sets — the gap measured between
them is entirely in the match-and-extract step, not in who saw a smaller haystack.

⚠︎ **THE BASELINE IS NOT AN HONEST FLOOR HERE, AND THAT IS MEASURED, NOT ASSERTED.** Once it
checks for an explicit record-id reference before falling back to anything fuzzy — the same thing
any quick script would obviously try first — it reaches **100% match accuracy on this corpus**,
identical to the model. The reason: the ONE disambiguating clue this corpus plants for its 29
genuinely ambiguous messages, "(currently at N units on our records.)" or "(currently scheduled to
ship &lt;date&gt;.)", is a SINGLE FIXED PHRASING with no variation — unlike, for example,
`data-reconcile`'s supplier-agreement clauses, which are written in two or three hand-authored
phrasings specifically so a fixed regex cannot cover them all. A regex written against this
corpus's one template catches every instance. This was found AFTER the real, paid run
(`r001-change-impact`) had already been fired once, and the run was not repeated to manufacture a
larger gap — see `Business.not_good_enough` on the published report for the full account. A future
revision of this corpus should vary the hint's phrasing the way `data-reconcile` varies its
clauses; `tools/build_corpus.py`'s `_hint_for()` is where that change belongs.

⚠︎ **An invented corpus contains the traps we thought to plant and no others.** A real vendor's
correspondence carries ambiguity this one does not attempt — a message that discusses two records
at once, a reply chain where the actual request is buried three quotes down, a typo'd record
number that resolves to nothing. A checker that clears this corpus has cleared what this corpus
tests, not every way a real message can be unclear.

⚠︎ **At most one requested change per message.** A real email can ask for several changes across
several line items at once; this corpus plants exactly one change per message to keep per-type
accuracy legible. `breaks_on` on the published report says this plainly.
