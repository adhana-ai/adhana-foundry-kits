# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every invoice record and every vendor
inquiry from a fixed seed (`SEED = 20260819`), so the corpus is byte-identical on every rebuild and
there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260819` |
| licence | **MIT** -- this repository's own licence |
| invoices | 35 in `data/invoices.jsonl`, each carrying a full 4-stage record and one vendor inquiry |
| gold | 35 rows in `data/gold.jsonl` -- `current_stage`, `requires_ap_review`, `expected_date`, and the trap flags below |
| vendors, invoice numbers, PO numbers, amounts | all invented; no real vendor or company appears anywhere in this corpus |

## Why an invented payment run, when real ones exist

**Because a real one cannot be published at all.** A real vendor payment run names a real vendor, a
real bank reference and a real approval chain -- this repo has never held one and is not able to.
There is no public corpus of paired (invoice trace, vendor inquiry, adjudicated current stage)
records, for the same reason no public corpus of production alerts or supplier agreements exists:
the interesting cases are exactly the ones nobody can publish.

## The mechanic this corpus tests

Every invoice carries all four stages -- match, approval, run_inclusion, remittance -- **always
fully populated**, whatever their state. The TRUE current stage is whichever of the four is the
actual bottleneck, read **in order**: match first, then approval, then run_inclusion, then
remittance. `requires_ap_review` is derived from `current_stage`, never authored independently --
true if and only if the governing stage is `match_exception` or `approval_exception`.

| stage | means | of 35 |
|---|---|---|
| `match_exception` | `match.matched` is false | 6 |
| `approval_exception` | match clean, `approval.status` is `exception` | 8 |
| `awaiting_run_inclusion` | match + approval clean, `run_inclusion.included` is false | 6 |
| `in_scheduled_run` | match + approval + run_inclusion clean, `remittance.remitted` is false | 8 |
| `remitted` | all four stages clean and `remittance.remitted` is true | 7 |

## The trap, planted on purpose

**6 of the 14 exception-stage invoices (~43%, the same order of magnitude as fin-invval's 45%
ambiguous-line design) are built so a downstream field still looks complete** while an earlier
stage is the one that actually governs -- 4 where `remittance` shows a real `remittance_date`,
`method` and `reference` despite an open match or approval exception, and 2 where `run_inclusion`
shows a real `run_id` and `scheduled_date` (a run the invoice was later pulled from) while
`remittance.remitted` is still false and the exception is still open. Remittance is the more common
trap field on purpose -- it is the one field whose false positive the eval exists to catch, named
`false_paid` in `evals/scoring.py`.

**This is a data-shape trap, not adversarial text.** Nothing in any field is written to deceive --
every value is exactly what it says, and no reason text claims something untrue. The trap is
entirely structural: a downstream field can be complete while an earlier one is not, and the only
way to get the invoice's true current stage right is to read match and approval before trusting
what run_inclusion or remittance show. `derive_stage()` in `tools/build_corpus.py` is the single
implementation of that precedence rule; it labels gold at generation time and, independently, via
`--verify`, re-checks every row against the invoice record actually written to disk.

`data/gold.jsonl` carries the trap explicitly, so a scorer never has to reverse-engineer it from the
record: `trap` (true/false), `trap_field` (`"remittance"`, `"run_inclusion"`, or null), and
`downstream_paid_looking` (whether `remittance.remitted` is true in the record, regardless of
whether that invoice is actually a planted trap). `false_paid`'s denominator in `evals/scoring.py`
is exactly the `trap` rows where `trap_field == "remittance"` -- gold non-remitted invoices with a
stale downstream remittance field present.

## What it cannot tell you

⚠︎ **This kit assumes match, approval and run-inclusion status all live in systems it can query
directly.** A manually tracked approval step -- an email sign-off that never made it into the
approval system -- has no trace to follow, and this corpus does not attempt to model that gap. A
real deployment would need to detect "the trail is incomplete" as its own state, distinct from
"the trail says exception"; this corpus's every invoice has a complete trail by construction.

⚠︎ **The trap denominator is small.** 4 remittance-trap invoices is what a corpus of this scale
supports honestly; a wider real deployment would want a larger sample before trusting the
`false_paid` rate as a stable number. It is reported as a raw count alongside the rate for exactly
this reason -- see `evals/scoring.py`.

⚠︎ **Every invoice carries at most one trap pattern.** A real payment run can carry a stale field
at more than one stage on the same invoice at once; this corpus plants at most one per invoice to
keep the failure mode legible.
