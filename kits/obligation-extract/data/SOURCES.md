# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every contract pack from a fixed seed
(`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `obligation-extract-2026-08-22-50contracts` |
| licence | **MIT** — this repository's own licence |
| packs | 50, in `data/corpus/*.txt`, 122,113 bytes |
| ordered lines | 275, across the 50 packs |
| decoy codes | 39 — 13 lines struck by an amendment, 14 professional-services rate cards, 12 items continuing under an earlier order form |
| gold | 50 rows in `data/gold.jsonl`, one per pack, each carrying its ordered lines and its decoys |
| worksheet rulebook | `data/rulebook.json` — **written for this kit**, see the warning below |
| customers / order forms / line codes / fees | invented names, invented references, invented amounts, with no link to any real company, supplier, product, contract or transaction |

## ⚠︎ The worksheet rulebook is illustrative and is NOT an authority

**`data/rulebook.json` was authored for this kit.** It reproduces **no** accounting standard, **no**
standard-setter's guidance, **no** audit firm's manual and **no** company's own revenue policy, and
it names none of them. Nothing in it was copied from, derived from, or checked against any such
document, because none was consulted. No standard number, no standard-setter, no audit firm and no
software vendor is named anywhere in this kit.

It is a small, deliberately readable construction whose only job is to make one decision *shape*
measurable: three stated facts are read off a contract line — what the fee column says, what the
clause says about how the line relates to the other ordered lines, and what it says about when the
line is supplied — and two calls come out of them, each of which may be `not_determined`. Several
of its simplifications are visibly not how a real review works, and are named as such in the file
itself — most obviously step 3, which records an explicitly-free line with the line it rides on
purely because the order form gives it no price and the contract says nothing else about it.

**The real authority for any determination is the framework the reporting company applies, and the
controller who applies it.** This kit produces **a reviewer's worksheet and never an accounting
conclusion**: it names what the paperwork states, applies the shipped rulebook, and names the calls
the paperwork does not settle. It never determines a performance obligation, never allocates a
transaction price, never concludes on timing, never opens a revenue schedule and **never writes,
posts, approves or dispatches anything**. That sentence is on the kit's own UI, above the answer,
and not only here.

## Why an invented set of contracts, when real ones exist

**Because a real subscription contract is not something this repo can publish either.** It names a
real customer, a real vendor's product and edition, real money, and terms both sides consider
commercially confidential. There is no public corpus of (contract, correct worksheet) pairs, for
the same reason there is no public corpus of bank statements or cleaning certificates.

Generating it also makes the label mechanical: gold's `separation` and `pattern` are the shipped
rulebook's own lookup run over the same three facts the pack itself states, never somebody's
reading of what the deal "really" is.

## The mechanic: one call per pack, a list back

Each pack states a contract id, a customer reference, an order form with its lines and their fee
column, one clause section per line, and — on most packs — one or more decoy sections. The model
returns the contract id and **one object per ordered line**, each with eight fields: the line code,
its description, its type, the three stated facts, and the two calls. See `src/prompt.py`.

**The rulebook is sent with every call.** Both calls are lookups over a shipped rule, and a model
cannot look up a rule it has never been shown. `src/rulebook.py::rulebook_block()` renders
`data/rulebook.json` into the prompt rather than restating it in prose, so the model's instructions
and the gold labels cannot drift apart about the same rule. Measured on the worked example: **847 of
3,067 input tokens (27.6%) are the rulebook**, and the fixed prefix — system prompt, rulebook and
field schema — is **2,346 of 3,067 (76.5%)**.

## The rule, and the step a confident reader skips

```
separation(charge, dependency):
    dependency == required_first                   -> bundled
    dependency == separately_available             -> distinct   (whatever the fee column says)
    dependency == silent AND charge == no_separate_charge -> bundled
    otherwise                                      -> not_determined

pattern(timing):
    timing == period  -> over_time
    timing == event   -> point_in_time
    timing == silent  -> not_determined
```

Four things about that rule are stated to the model in full, because each is a reading a careless
reviewer falls into on its own — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **a price is not a statement about separability** | a line with a fee of its own and nothing said about whether the customer could take it alone is `not_determined`. It is the most attractive wrong answer on the page, and on this rulebook it is wrong rather than arguable | **70 lines** |
| **a line priced at nothing can still be `distinct`** | when the contract says the customer may cancel or source it separately, that settles it and the fee column does not get a vote | **23 lines** |
| **a line priced at nothing with nothing said is `bundled`** | one clause away from the case above, which is the point of having both | **40 lines** |
| **the pattern is asked independently of the separation call** | a bundled line still either has a stated window, a stated event, or neither | **70 lines** state neither |

The rule lives in one module — `src/rulebook.py` — used to write gold, stated to the model by
`src/prompt.py`, and re-run over the model's own reply by `evals/judge.py`. Three readers, one
definition, so the corpus, the prompt and the diagnostic cannot drift about what a call means.

## The planted decoys: three ways to put a promise on a worksheet that is not one

39 codes across the 50 packs are in the same `PO-nnnn` format as a real line and are **not**
obligations:

- **a line struck by an amendment (13)** — its code and its description are on the order-form row,
  marked withdrawn, **and its whole clause section is still printed in the pack**. Only the row and
  the Contract Notes say it was removed. A reader working from the clauses lists it;
- **a professional-services rate card (14)** — a coded day rate, with the pack stating in terms that
  no services are ordered under this order form. A price is not a promise;
- **an item continuing under an earlier order form (12)** — supplied under somebody else's
  paperwork, referred to here for context.

`evals/baseline.py` — the free floor — lists all 13 struck lines, because it reads the order-form
rows and never reads the amendment beside them.

## The composition is exact, then dealt — not drawn per line

Each bucket is a fixed **count**, allocated by the seeded RNG over the slots whose line type can
carry it, and the allocator raises rather than back-filling: a corpus that cannot be built to its
own design is a design problem, not something to paper over at generation time.

| `bundled` | 85 |

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises `needs_drafting_review` when the pack carries at least one line
the order form **prices** — a fee of its own — whose `separation` **and** `pattern` the paperwork
settles neither of. An open call on an unpriced line is drafting untidiness; the same open call with
money attached is a number somebody will have to place, and the contract says neither where it goes
nor when.

⚠︎ **The narrower condition was chosen over the obvious one, and the reason is measured.** "A priced
line whose separation is open" fires on **41 of the 50 packs** — 82% — and a flag that is almost
always on is a flag nobody reads and a grader that scores well by saying yes. Requiring both calls
to be open splits the corpus properly, at 12 of 50.

⚠︎ **This is the kit's own simplification, not any company's review policy.** No revenue policy,
audit manual, accounting standard or standard-setter's guidance was consulted, and none is
reproduced. A real review weighs the fee against materiality, what the sales team can tell you that
the paperwork cannot, whether a side letter exists, and what the same customer's previous orders
said.

## What it cannot tell you

⚠︎ **This kit builds a worksheet only — it never reaches an accounting conclusion.** `separation`
and `pattern` are proposals with the rulebook's own reasoning attached, and `needs_drafting_review`
is a routing signal. Nothing here determines an obligation, allocates a price, concludes on timing,
opens a schedule or writes an entry.

⚠︎ **A run that scores perfectly has agreed with `data/rulebook.json`, which is a much smaller claim
than being right about a real contract.** The graders measure whether the run applied the shipped
rulebook. They cannot measure whether the rulebook is correct, because the rulebook is this kit's
own construction and nobody qualified has reviewed it.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real review
queue carries confusions this one does not attempt — a side letter that contradicts the order form,
a master agreement whose terms override every line, a discount applied across lines so no line's own
price means anything, an amendment signed after the period end, a currency or a payment schedule
that changes the answer, and language written to be ambiguous rather than merely silent. A model
that clears this corpus has cleared what this corpus tests, not every way a contract review can go
wrong.

⚠︎ **And this corpus has one confusion it did not set out to plant, found by running it.** A line
whose *dependency* clause names an acceptance or completion moment — "not made available until the
implementation acceptance certificate is signed" — while stating no delivery timing of its own is
genuinely confusable, and the scored run answered `point_in_time` on 6 of the 11 lines shaped that
way. Gold treats them as `not_determined` because the rulebook's timing question is about when the
*line* is supplied, and a prerequisite clause is about what cannot happen until it is. That
distinction is real and it is also thin, and it is named here rather than defended.
