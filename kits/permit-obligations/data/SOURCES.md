# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every obligation register from a fixed
seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `permit-obligations-2026-08-22-50registers` |
| licence | **MIT** — this repository's own licence |
| registers | 50, in `data/corpus/*.txt`, 114,032 bytes |
| obligations | 268 condition blocks across those 50 registers, 4 to 7 per register |
| gold | 50 rows in `data/gold.jsonl` — one per register, each carrying its own obligations |
| obligation rulebook | `data/rulebook.json` — **written for this kit**, see the warning below |
| sites / permits / offices / conditions | invented site names and identifiers, invented permit numbers, invented administering bodies, invented condition identifiers and waiver references, with no link to any real operator, mine, site, permit, regulator or regulation |

## ⚠︎ The rulebook is illustrative and is NOT an authority

**`data/rulebook.json` was authored for this kit.** It reproduces **no** permit, **no** licence
condition, **no** regulator's guidance, **no** industry code and **no** statutory schedule. Nothing
in it was copied from, derived from, or checked against any such document, because none was
consulted. No real permit, operator, site or administering body is named anywhere in this kit.

It is a small, deliberately readable construction whose only job is to make the *decision shape*
measurable: does a condition still bind at all, does the register carry what the rule needs, when
does the next instance fall due, and is that date already past, inside the action window, or still
ahead. Several of its simplifications are visibly not how a real permit works, and are named as such
in the file itself — most obviously the idea that an obligation type has ONE interval and ONE action
window, when a real permit sets a period per condition and an amendment can move it.

**The real authority for any obligation is the permit instrument, its amendments, and the
administering body's own correspondence.** This kit proposes a status with its reasoning and names
what it could not determine. **It never authorises, files, submits, notifies, escalates, renews or
clears anything, and it watches nothing** — it reads one register that somebody else assembled, as
at the date printed on it. That sentence is on the kit's own UI, above the worklist, and not only
here.

## Why an invented set of registers, when real ones exist

**Because a real obligation register is not something this repo can publish either.** It names a
real site under a real permit, its actual compliance position, the conditions it has missed and the
ones it has been let off — which is commercially sensitive on one side and legally consequential on
the other. There is no public corpus of (register, correct worklist) pairs, for the same reason
there is no public corpus of bank statements or certificates of analysis.

Generating it also makes the label mechanical: gold's `status` and `due_date` are the rulebook
lookup run over the same values the register itself states, never somebody's reading of the site's
own flag.

## What a "monitor" kit is here, and what it is not

**A monitoring SNAPSHOT is the document.** Each file is one site's register at one moment: the
conditions that bind it, the intervals they run on, and what the record shows has actually been
done. The kit reads it once and answers one question — *which of these obligations needs action, by
when, and which ones cannot be determined from what is on the page?*

It is **not** a daemon, a stream, a scheduler or a dashboard. There is no poller, no queue, no cron
and no state. `requirements.txt` says so out loud, because a monitoring kit is the one place a
reader might expect a job runner and there is none.

## The mechanic: one call per register, 11 fields

Each register states a site, a permit and an issuing office, the date the register was drawn, the
site's own summary note, and then one block per permit condition: what it requires, its type, its
state, the date it was last recorded as done, the reporting period a filing was credited to, any
stated due date, the state of its trigger event, and the site's own flag for the row. The model
extracts **3 register-level fields and 8 per obligation** — everything except the site's summary
note, which no field maps to and which is therefore never sent. See `src/prompt.py`.

**The model never returns a status.** `src/rulebook.py::decide()` computes it afterwards, in pure
code, from the values that came back. Every status error on this page is therefore an inherited
*reading* error, and the false-alarm rate is a measurement of reading accuracy propagated through a
rule — which is exactly what a monitoring desk is buying.

## The rule, and the stopping order a reader gets wrong

```
status(register_date, obligation):
    no readable register date, unknown state, unknown type      -> not_determinable
    condition superseded by an amendment, or waived in writing   -> not_binding   (dates irrelevant)
    event-triggered and the trigger has NOT occurred             -> not_yet_due   (a recorded fact)
    event-triggered and the register does not say                -> not_determinable
    cycle type with no last-done date                            -> not_determinable
    annual report with no reporting period credited              -> not_determinable
    -- otherwise derive the due date --
      cycle:            last_done + the type's interval
      annual report:    31 March of the year after the year AFTER the period credited
      event-triggered:  the due date the register states
    due date before the register date                            -> overdue
    due date within the TYPE'S OWN action window                 -> due_in_window
    beyond it                                                    -> not_yet_due
```

Five things about that rule are stated to the model in words, because each is a reading a careless
monitor falls into on its own — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **a superseded or waived condition still binds nothing** | it is still printed on the register, still carries a stale date, and computes as overdue if you read dates before you read the state | **32 obligations**, and `evals/check_labels.py` asserts every one of them would land on the worklist with the state ignored |
| **an annual report is measured by its PERIOD, not its filing date** | a report filed last month can be the report for a reporting year two years back, leaving the year in between outstanding | **22 obligations** are overdue while showing a filing dated inside the last 90 days |
| **a dateless entry cannot date the next one** | a reading recorded as taken with the date column empty is `not_determinable`, and answering anything else is a guess | **16 obligations** |
| **"has not occurred" and "not recorded" are different facts** | the first means nothing is due; the second means nobody can tell. Merging them turns an unknown into a clearance | **20** against **10** |
| **the action window is per type, not one number** | a financial assurance gets 60 days because re-lodging a security is arranged with a third party; everything else gets 30 | **13** financial assurances and **17** readings/inspections fall due 31–60 days out — the same distance, opposite answers |

The rule lives in one function — `src/rulebook.py::decide()` — used to write gold, stated to the
model by `src/prompt.py` as context for why each field matters, and run over the model's own reply
by `src/extract.py`. Three readers, one definition, so the corpus, the prompt and the scorer cannot
drift about what a status means.

## The planted contradiction: the site's own flag disagrees with the rulebook

`N_MISFLAGGED = 107` puts a `Register flag` from the wrong register on exactly 40% of the
obligations:

- a condition that is already overdue, flagged `on track`;
- a superseded condition that binds nothing, flagged `attention`;
- a reading falling due next week, flagged `closed`.

Gold's `status` is **never** derived from the flag. It is the rulebook lookup, run over the same
values the register itself states. The flag is extracted, is published on every row, and decides
nothing.

## The composition is exact, then shuffled — not drawn per row

Each of the thirteen buckets is a fixed **count**, shuffled by the seeded RNG and dealt into
registers of 4–7 conditions, and every constructor is asserted against the rulebook at build time —
a constructor that quietly stops producing its own bucket is exactly the defect an exact composition
exists to prevent.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises an escalation when at least one obligation the rulebook makes
`overdue` carries a `Register flag` of `on track` or `closed`. An overdue row already flagged
`attention` is a site that knows. An overdue row the site's own tracker calls fine is the other
thing entirely: nobody is looking, and chasing the site's own list will never surface it.

⚠︎ **This is the kit's own simplification, not any real escalation policy.** No permit,
regulator's guidance or operator's procedure was consulted, and none is reproduced. A real
compliance function weighs which condition lapsed, by how long, whether the breach is reportable in
its own right, whether the administering body already knows, and who is authorised to disclose it.

## What it cannot tell you

⚠︎ **This kit reads and proposes only — it never files, notifies, escalates, renews or clears, and
it watches nothing.** `status` is computed and `escalate` is a routing signal; nothing here acts,
and nothing here continues after the call returns.

⚠︎ **A run that scores perfectly has agreed with `data/rulebook.json`, which is a much smaller
claim than being right about a real permit.** The graders measure whether the run read the register
the shipped rulebook is applied to. They cannot measure whether the rulebook is correct, because
the rulebook is this kit's own construction.

⚠︎ **An invented corpus contains the noise we thought to plant and no others.** A real obligation
register carries confusions this one does not attempt — a condition whose text is ambiguous about
its own frequency, an amendment that changes an interval mid-cycle, an obligation recorded against
the wrong condition number entirely, a due date extended by correspondence that never reached the
register, two conditions that overlap, a site with several permits whose registers disagree, and
evidence filed but not linked to the condition it discharges. A run that clears this corpus has
cleared what this corpus tests, not every way an obligation register can go wrong.
