# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every CAM reconciliation line from a
fixed seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `cam-precheck-2026-08-22-55lines` |
| licence | **MIT** — this repository's own licence |
| records | 55, in `data/corpus/*.txt`, 53,655 bytes |
| gold | 55 rows in `data/gold.jsonl` |
| properties / tenants / agents | invented statement identifiers and invented managing-agent names, with no link to a real landlord, tenant, property or executed lease |

## Why an invented set of reconciliation lines, when real ones exist

**Because a real CAM reconciliation line is not something this repo can publish either.** It names
a real tenant, a real property, a real landlord's general-ledger detail and a property
accountant's own note about a specific account. There is no public corpus of (reconciliation line,
correctly-computed tenant share) pairs, for the same reason there is no public corpus of bank
statements or utility billing records — and here there is a second reason on top of it: the answer
depends on **that tenant's own negotiated lease**, which is a confidential document even where the
building is public.

**No executed lease, published lease form, industry standard form, real landlord, real tenant or
real property is named or reproduced anywhere in this kit.** "Operating expenses", "gross-up",
"pro-rata share", "amortization" and "cap" are ordinary commercial-lease vocabulary; every
identifier, managing agent, expense category, cap term and accountant note here was invented for
this corpus.

## The mechanic: one call per line, twenty fields

Each record states one expense line as it would appear on a tenant's reconciliation: the statement
line id, the managing agent, the expense category and its structured class, the gross pool cost at
the property, whether the lease permits amortizing it, whether it varies with occupancy, the
building's occupancy and total area, the tenant's area and any mid-year expansion, the lease's cap
terms, what the landlord actually billed, whether the statement has been issued, and the property
accountant's own note.

The model extracts eighteen of those verbatim and **computes two**: `permitted_amount_usd`, the
dollar figure the lease actually allows, and `line_ok`, the comparison of that figure against what
was billed. **Everything except the managing agent is sent** — no field maps to it, so selection
drops it and it never reaches the provider. See `src/select.py` and `src/prompt.py`.

## The rule, and the order a reader who knows the vocabulary still gets wrong

```
permitted(line):
    STAGE 1  poolable    landlord_overhead / leasing_cost        -> 0
                         capital_improvement, no amortization    -> 0
                         capital_improvement, amortized over N    -> gross / N     (ONE instalment)
                         routine_operating                       -> gross in full
    STAGE 2  gross-up    occupancy_sensitive == yes AND occupancy < 95
                                                                 -> x 95 / occupancy
    STAGE 3  pro rata    x (tenant_area + expansion x (13 - month) / 12) / building_area
    STAGE 4  cap         annual      -> min(amount, basis x (1 + pct/100))
                         cumulative  -> min(amount, basis x (1 + pct/100) ** periods)
    line_ok = "yes" iff |billed - permitted| <= 1.00
```

The rule lives in **one function file** — `src/rule.py` — and five things read it: the generator
that writes gold, the prompt that states it to the model in words, the extractor that re-runs it
over the model's own reply, the scorer that re-derives gold's truth at score time, and the
pre-flight that refuses the run if a single label disagrees with it. There is no second copy to
drift.

Five things about that rule are stated to the model in full, because each is a reading a
practitioner falls into on their own:

| | |
|---|---|
| **an amortizable capital item is PARTLY billable** | "capital is excluded" is the rule most people carry, and on an amortizable item the lease permits one annual instalment — neither the whole cost nor zero. **8 of these 55 lines** are amortizable capital |
| **the category NAME is a label, the CLASS is the classification** | **14 of these 55 lines** carry a category called "Parking lot resurfacing", "Property management fee", "Roof membrane patching" or "HVAC compressor overhaul" on a line whose `expense_class` says `routine_operating`. The class decides |
| **the gross-up applies only to occupancy-sensitive lines** | grossing up an expense that does not vary with occupancy is an overcharge that looks exactly like diligence |
| **gross up BEFORE you cap** | **3 lines** carry a cap with slack against the ungrossed share that BINDS against the grossed-up one, so skipping stage 2 also silently skips stage 4. These are the sharpest records in the corpus |
| **a cumulative cap compounds** | applying it once, as though it were an annual cap, undercharges — the one fault direction here that costs the landlord rather than the tenant |

## The two planted ambiguities, and they are orthogonal

**(a) The note.** `N_AMBIGUOUS = 22` puts a property accountant's note from the wrong register on
exactly 40% of records:

- a materially wrong line carrying "Line agrees to the GL detail, no issues noted.";
- a line billed to the cent carrying "Escalated for manager review; the allocation basis on this
  line is disputed."

**(b) The category name.** `N_DECOY_CATEGORY = 14` puts a name that reads like an exclusion on a
line the lease permits in full. A reader can resist the note and still write zero on the name.

Gold is **never** derived from either. It is the four-stage arithmetic, run over the same values
the record itself states.

## The eight faults, and why none of them is a random number

A wrong line here is the same pipeline with exactly **one stage broken** — `wrong_amount()` in
`tools/build_corpus.py` recomputes the whole rule with one input deliberately mis-set, so the
billed figure is the number a person actually arrives at rather than noise:

| fault | n | direction | what somebody did |
|---|---|---|---|
| `capital_full_cost` | 4 | overcharge | billed the tenant's share of the whole capital cost, not one instalment |
| `excluded_billed` | 4 | overcharge | pooled an excluded line as though it were an operating expense |
| `grossup_missing` | 4 | undercharge | did not gross up an occupancy-sensitive line in a partly-vacant building |
| `grossup_wrong_class` | 3 | overcharge | grossed up a line that does not vary with occupancy |
| `cap_ignored` | 5 | overcharge | billed the uncapped share where the ceiling binds |
| `cap_not_compounded` | 3 | undercharge | applied a cumulative cap once, as though annual |
| `prorata_start_area` | 3 | undercharge | used the start-of-year area and ignored the expansion |
| `prorata_full_year_expansion` | 2 | overcharge | applied the expanded area to all twelve months |

⚑ **And every fault is asserted to move the billed figure by at least `MATERIALITY_USD = 25.00`**,
so no `line_ok` label is a coin flip on the last cent. Without that floor the corpus would be
measuring floating-point luck and publishing it as reasoning. `evals/check_labels.py` re-asserts it
over every gold row before any run may spend.

## "Correct" is not the easy interior of the rule either

The 27 correctly-billed lines are drawn from eight shapes, so every trap appears on **both sides**
of the verdict: `amortized_capital` (4), `excluded_zero` (3), `grossup_applied` (4), `cap_binding`
(3), `cap_binds_after_grossup` (3), `cumulative_cap` (3), `expansion` (4), `plain` (3). A corpus
where every hard branch is a wrong answer teaches a model to answer "no" whenever it sees a cap.

## The composition is exact, then shuffled — not drawn per record

Several sibling kits in this series draw each record's class from an independent coin, which is
fine at 500 records and is not fine at 55 — a kit two before this one asked for 40% ambiguity and
delivered 51%. So each class here is a fixed **count**, shuffled by the seeded RNG.

The mix on this seed:

| | |
|---|---|
| billed correctly | 27 |
| billed wrong | 28 |
| — of which overcharges (against the tenant) | 18 |
| — of which undercharges (against the landlord) | 10 |
| accountant note from the contradicting register | 22 (40%) |
| category NAME that reads excludable on a routine line | 14 |
| amortizable capital — partly billable | 8 |
| a cap that binds only after the gross-up | 3 |
| statement already issued | 33 |
| overbilled **and** already issued — the review flag | **7** |

⚠︎ **That last denominator is small, and it is named here rather than hidden.** Seven records means
one miss moves the flag's recall by 14.3 points, which is exactly what happened between this kit's
two runs. `evals/check_labels.py` prints the same warning before any run is allowed to spend.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` routes a line for a corrected statement when it is billed wrong **and**
the error runs against the tenant **and** the statement has already been issued. A wrong line still
in draft can simply be corrected before release — that is what a pre-check is for. The direction
matters because an overcharge is what a tenant's auditor claws back; an undercharge is money the
landlord did not collect, which is real and is nobody's emergency.

⚠︎ **This is the kit's own simplification, not a real property-accounting policy.** No lease's
audit-rights clause, no reconciliation deadline and no landlord's release procedure was consulted,
and none is reproduced. A real desk weighs the dollar size against the audit threshold, how many
cycles the same error has run, and whether the tenant's audit window is still open at all.

⚠︎ **And it reads a COMPUTED field**, so it inherits every arithmetic error. That is not a defect
in the design, it is the design being honest: on run `r002` a single wrong permitted amount turned
a $1,117 overcharge into an apparent undercharge and the flag did not fire, while the verdict grade
still read 100%.

## What it cannot tell you

⚠︎ **This kit checks and routes only — it never issues a corrected statement, credits a tenant or
releases a reconciliation.** `line_ok` is a computed field and `needs_review` is a routing signal;
nothing here disposes of anything, and the catalogue entry this kit answers says so too: a human
releases.

⚠︎ **The cap here is applied per LINE, and a real lease caps the aggregate.** A commercial
operating-expense cap almost always ceilings the tenant's total controllable pool for the year, not
each line independently. Capping the line is what lets one record be one call, and it is a
simplification a forker must replace before checking anything real.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real
reconciliation queue carries confusions this one does not attempt — a base-year stop rather than a
cap, an admin fee computed on a pool that already includes it, an expense allocated across two
buildings under one lease, a tenant whose lease defines rentable area differently from the
landlord's own measurement, or a controllable/uncontrollable split the cap only touches half of. A
model that clears this corpus has cleared what this corpus tests, not every way a CAM
reconciliation can go wrong.
