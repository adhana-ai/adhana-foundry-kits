# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every session, every event's per-store
asks and commitments, every merchant note and the gold flag/cause list from a fixed seed
(`SEED = 20260818`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all. The written allocation policy it runs (`data/POLICY.md`) is authored for
this kit too — see that file's own header for why.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260818` |
| licence | **MIT** — this repository's own licence |
| sessions | 40, in `data/sessions.jsonl` — each carrying 4-6 shortage events across 6-10 stores |
| notes | 40 rows in `data/notes.jsonl` — one merchant-notes log per session |
| gold | 40 rows in `data/gold.jsonl` — every event's flag state, true cause and citations |
| formats | jsonl (sessions, notes, gold), md (the written policy) |

## Why an invented allocation corpus, when public retail datasets exist

**A public dataset was considered and set aside, deliberately, not for convenience.** Public
inventory and demand datasets — Kaggle's retail and demand-forecasting sets among them — carry
SKU-level sales and stock numbers, and some carry licences permissive enough to redistribute. What
none of them carry is the one thing this eval's own `eval_intent` actually asks for: *"prove the
drafted split matches what approved allocators did."* That needs a paired record of (a shortage
event, a written policy it was resolved against, and the decision a human allocator actually
made) — and real allocator decisions are commercially sensitive operational data no retailer
publishes, for the same reason no retailer publishes its markdown calendar or its vendor
scorecards. A public sales-history file could supply plausible *asks*; it cannot supply the *gold
label this kit is graded against*, so bolting one on would have produced a corpus that looks more
real while measuring nothing more than before.

**It would also have reopened the exact problem the self-authored route exists to avoid.**
`data-match`'s own `SOURCES.md` makes the same call for its own corpus: *"the alternative is a
licence argument we would lose... generating the corpus removes the question entirely."* A Kaggle
dataset's licence terms vary file to file, and several of the well-known retail-allocation-flavoured
sets on Kaggle are released for competition or research use only, not commercial redistribution —
exactly the kind of licence a public kits repo cannot safely carry without reading every terms
page one more time. Generating the corpus removes that reading entirely.

**Nothing in here refers to a real company.** Every store, SKU, region and merchant-note line is
invented; no row here states a real commercial figure.

## Five scenarios, planted so flag completeness, cause-tagging and honesty are all worth telling apart

| scenario | what it is | cause the model should reach |
|---|---|---|
| `clean` | promo and customer commitments both fully protected, fair-share clears the 40% equity floor for every store | n/a — not flagged |
| `promo_overcommit` | promo commitments across stores exceed available on their own | `promo_overcommit`, traceable |
| `customer_overcommit` | customer pre-order commitments exceed what the reservation system actually held | `customer_overcommit`, traceable |
| `demand_surge` | nobody over-promised; a genuine, unplanned velocity spike makes the ordinary math infeasible | `demand_surge`, traceable |
| `supply_shortfall` | the DC itself received fewer units than the supply plan assumed | `supply_shortfall`, traceable |
| `unknown_flag` | a real, material shortfall — the notes do not explain why | `unknown`, correctly unresolved |

`src/allocate.py::EQUITY_FLOOR_PCT = 40.0` and the `clean`-scenario supply band
(85–97% of total ask) are stated judgements, sized so the flag signal is measured clean rather
than assumed: `tools/selftest_allocate.py` asserts the `clean` scenario is flagged 0% of the time
and every planted-defect scenario is flagged at least 90% of the time, on every corpus rebuild —
not a one-time check, a standing gate.

## The gold cause is never inferred by the pipeline's own code

`tools/build_corpus.py` decides each event's scenario and (for the four traceable causes) its
exact two explanatory notes lines at generation time — all before `src/allocate.py::allocate` ever
runs. The pipeline recomputes the flag independently, from the event's own ask/commitment/velocity
numbers alone, using the identical five-clause policy the generator was sized against; it never
reads `data/gold.jsonl`. How well a model's cause tag matches the gold cause is therefore a real,
measured question — never a tautology.

## The protected-class guardrail is measured, not promised

`trade_area_tier` is generated per store and carried in `data/sessions.jsonl` for a reader to
audit — but `src/allocate.py::allocate` never takes it as a parameter, so the code-computed split
cannot use it even if someone tried. `evals/parity_check.py` proves the CONSEQUENCE of that
exclusion with a permutation test: shuffle each event's tier labels among its own stores 500
times and confirm the real labelling's tier-to-tier spread in allocated fraction is not more
extreme than chance. Measured result on this corpus: **p = 0.42** — parity holds.

## What this corpus does not test

- **One static event, not a rolling history.** A real deployment would see the same SKU recur
  shortage-week over shortage-week; this corpus judges every event independently.
- **One planted cause per event.** A real shortfall can have two compounding causes at once; this
  corpus always plants exactly one (or none, for `unknown_flag`).
- **Two events in the same session sharing a root cause.** Every event's scenario is drawn
  independently in `tools/build_corpus.py`.
- **A cause outside the five-member vocabulary.** A real allocation review will eventually name a
  cause this kit's fixed list does not carry; extending it is a `src/rubric.py` change plus new
  template notes in `tools/build_corpus.py`, not a prompt tweak alone.
- **A written policy with more than five clauses**, or clauses that themselves conflict — this
  kit's policy is deliberately simple so its arithmetic is auditable; `data/POLICY.md`'s own
  closing section names what a real deployment's policy would need to add.
