# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every history event, every planned
request and every gold label from a fixed seed (`SEED = 20260818`), so the corpus is
byte-identical on every rebuild and there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260818` |
| licence | **MIT** — this repository's own licence |
| history events | 120, in `data/history.jsonl` — 24 per category across 5 categories |
| requests | 15 in `data/requests.jsonl` — 3 per category |
| gold | 360 pairwise rows in `data/gold.jsonl` — `analog` / `not_analog` for every (request, blocked candidate) pair |
| formats | jsonl (history, requests, gold) |

## Why an invented promotion calendar, when real ones exist

**Because a real one cannot be published at all.** A real promotion's mechanic, price point and
measured lift is exactly the kind of commercial detail a retailer will not let leave the building.
There is no public corpus of paired (planned request, prior comparable events, adjudicated
analog/not-analog, measured lift) tuples, for the same reason no public corpus of production
alerts or signed supplier agreements exists.

**Nothing in here refers to a real retailer, brand or product.** Categories, mechanics and lift
figures are invented.

## The job is generic; the flavour is not

This kit's actual job — match a new planned item against prior comparable cases on a stated set
of attributes, and draft a quantified estimate from the closest matches — applies to anything with
a precedent to lean on: a pricing change against comparable past changes, a staffing plan against
comparable past events, a hiring band against comparable past roles. This corpus happens to flavour
the "planned item" as a retail promotion and the "attribute set" as mechanic / price band / ad
placement / season, because that is one concrete, checkable instance of the job, not because the
job is about retail. Point `tools/build_corpus.py` at your own attribute set and the pipeline —
`src/block.py`, `src/prompt.py`, `src/lift.py` — does not change.

## The ANALOG rule, planted and counted

A candidate history event is a true analog for a request only if **all four** hold: identical
mechanic, identical-or-adjacent price band (on the fixed order `under_5, 5_10, 10_25, 25_plus`),
identical ad placement OR both in the paper-circular family `{circular_front, circular_inside}`,
and identical season. `src/tools/build_corpus.py::is_analog()` is that rule in code; it is also
`src/prompt.py`'s `RULES` text verbatim in prose, so the two cannot silently drift apart.

Every request gets **3 deliberately planted analogs** (one exact match, one exercising the
price-band allowance, one exercising the placement-family allowance) and **4 deliberately planted
near-misses** (each violating exactly one of the four rules), plus 3 unshaped filler events per
category. `is_analog()` is then applied uniformly to the whole category pool — a filler event that
happens to satisfy the rule by coincidence is labelled `analog` too; nothing is hand-labelled after
the fact. Of the 360 pairwise rows this produces, 50 (13.9%) are `analog`.

## What the exact-match floor cannot tell you

⚠︎ **THE FREE FLOOR (`evals/baseline.py`) IS A REAL BASELINE, NOT A STRAWMAN, AND IT REUSES THE
SAME BLOCKING CODE THE REAL PIPELINE RUNS** (`src/block.py`), so the two are compared on identical
candidate sets — the gap measured between them is entirely in which pairs get counted as analogs,
never in who saw a smaller haystack.

⚠︎ **BY CONSTRUCTION, THE FLOOR CAN NEVER FALSE-MERGE ON THIS CORPUS.** It only counts a
candidate as an analog when all four fields match literally (`src/similarity.py`, threshold 1.0),
and any pair with all four fields literally identical also satisfies the true ANALOG rule (identity
is a special case of "identical or adjacent" and "identical or family"). So its errors, if any, are
entirely on the recall side: the two planted allowances — an adjacent price band, a
circular-placement swap — are exactly the cases a field-equality score cannot see. Whether the
model actually recovers that gap is measured, not assumed; see the published Eval lens for the real
number.

⚠︎ **AN INVENTED CORPUS CONTAINS THE TRAPS WE THOUGHT TO PLANT AND NO OTHERS.** A real promotion
calendar carries ambiguity this one does not attempt — a mechanic that changed mid-run, a placement
that was booked but not delivered, a season boundary that is itself disputed. A checker that clears
this corpus has cleared what this corpus tests, not every way a real precedent can be unclear.

⚠︎ **discount_depth_pct AND duration_days ARE CONTEXT, NEVER DECISIVE.** Both are shown to the
model and both vary freely across analogs and near-misses alike — a candidate at a very similar
discount depth is not an analog if the mechanic, band, placement or season rule fails, and the
prompt says so explicitly. `Data.breaks_on` on the published report says this plainly.
