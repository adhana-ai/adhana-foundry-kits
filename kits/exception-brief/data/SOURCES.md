# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every review batch, every flagged
item/location's evidence packet, every merchant note and the gold exception list from a fixed seed
(`SEED = 20260818`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260818` |
| licence | **MIT** — this repository's own licence |
| batches | 40, in `data/batches.jsonl` — each carrying 5 flagged item/location candidates |
| notes | 40 rows in `data/notes.jsonl` — one merchant-notes log per review batch |
| gold | 40 rows in `data/gold.jsonl` — every item's materiality, true cause and traceable citations |
| formats | jsonl (batches, notes, gold) |

## Why an invented exception-review corpus, when real ones exist

**Because a real one cannot be published at all.** A real statistical-forecast exception queue
names real SKUs, real store/location identifiers and real POS volumes — exactly the material a
retailer will not let leave the building, on top of being the kind of internal planning
correspondence nobody signs an MIT licence over. There is no public corpus of paired (forecast,
recent POS, OOS/promo/prior-year evidence, merchant notes, adjudicated cause) for the same reason
there is no public corpus of internal demand-planning exception queues.

**Nothing in here refers to a real company.** Every region, store id, category label, review week
and merchant-note line is invented; no row here states a real commercial figure.

## The job is generic; the flavour is not

This kit's actual job — assemble the evidence for an automated forecast exception, itemize every
material item/location with a quantified deviation and a probable cause traced to real source
lines, and draft the review-meeting brief — applies to any deployment where a statistical baseline
throws exceptions against an actuals feed: a demand forecast against POS is one instance, an
inventory reorder point against consumption or a staffing plan against actual hours are others.
This corpus flavours it as a retail demand-planning exception queue — a statistical forecast versus
recent POS, across synthetic product categories, regions and store locations — because that is the
scenario the kit's originating use case names. Point `tools/build_corpus.py` at your own forecast
and actuals feed and the pipeline — `src/segment.py`, `src/pack.py`, `src/prompt.py` — does not
change.

## Seven scenarios, planted so completeness, cause-tagging and honesty are all worth telling apart

| scenario | what it is | cause the model should reach |
|---|---|---|
| `clean` | recent POS agrees with the statistical forecast within ordinary noise (±5%). Not itemized. | n/a — not material |
| `promo_uncaptured` | a promo not baked into the baseline explains an uplift | `promo_uncaptured`, traceable |
| `oos_suppressed` | a lost-sales/OOS period explains the deviation | `oos_suppressed`, traceable |
| `onetime_event` | a one-off, non-repeating local driver explains the move | `onetime_event`, traceable |
| `assortment_shift` | an item/pack/channel change broke comparability with the baseline | `assortment_shift`, traceable |
| `unknown_gap` | a real, material exception — the notes do not explain it | `unknown`, correctly unresolved |
| `data_quality_flag` | this item/location's recent POS is flagged unreliable (a register/data outage) | `unknown`, plus a mandatory unreliable-evidence caveat |

`src/segment.py::MATERIALITY_PCT = 18.0` is a stated judgement, not fitted to this corpus after
the fact — the same honesty `gap-brief`'s and `param-drift`'s own thresholds state. Clean items'
noise band (±5%) and defect items' shift band (22–48%) were sized in `tools/build_corpus.py` to sit
cleanly on either side of it; `tools/build_corpus.py --n-batches 40`'s own tally line prints the
resulting scenario counts on every rebuild so the split can never silently drift from what this
file claims.

## The gold cause is never inferred by the pipeline's own code

`tools/build_corpus.py` decides each item's scenario, its shifted actual and (for the four
traceable causes) its exact two explanatory notes lines at generation time — all before
`src/segment.py::flag` ever runs. The pipeline recomputes materiality independently, from the
forecast/actual pair alone, using the identical threshold the generator was sized against; it never
reads `data/gold.jsonl`. How well a model's cause tag matches the gold cause is therefore a real,
measured question — never a tautology.

## What this corpus does not test

- **One static review per item, not a rolling history.** A real deployment would see the same
  item/location recur review after review, sometimes still flagged from last time; this corpus
  judges every batch independently.
- **One planted cause per exception.** A real exception can have two compounding causes at once;
  this corpus always plants exactly one (or none, for `unknown_gap`).
- **Two items in the same batch sharing a root cause.** Every item's scenario is drawn
  independently in `tools/build_corpus.py`.
- **A cause outside the five-member vocabulary.** A real exception-review meeting will eventually
  name a cause this kit's fixed list does not carry; extending it is a `src/rubric.py` change plus
  new template notes in `tools/build_corpus.py`, not a prompt tweak alone.
