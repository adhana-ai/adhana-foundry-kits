# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every application, every document
value and every submission note from a fixed seed (`SEED = 20260819`), so the corpus is
byte-identical on every rebuild and there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260819` |
| licence | **MIT** -- this repository's own licence |
| applications | 36 in `data/applications.jsonl`, each carrying a declared record and three document blocks |
| gold | 36 rows in `data/gold.jsonl` -- a flag for each of 7 fields, `verification_outcome`, and the trap flags below |
| businesses, owners, addresses, tax IDs, bank details | all invented; no real business or person appears anywhere in this corpus |

## Why an invented onboarding batch, when real ones exist

**Because a real one cannot be published at all.** A real seller onboarding application names a
real business, a real owner and a real bank account -- this repo has never held one and is not
able to. There is no public corpus of paired (application, submitted documents, adjudicated
verification outcome) records, for the same reason no public corpus of KYC decisions or fraud
cases exists: the interesting cases are exactly the ones nobody can publish.

## The mechanic this corpus tests

Every application declares seven fields on the form and carries three verification documents --
business registration, bank letter, government ID -- **always fully populated**, whatever their
state. Each declared field is checked against exactly one document field:

| declared field | checked against |
|---|---|
| `business_name` | `business_registration.legal_name` |
| `business_address` | `business_registration.registered_address` |
| `tax_id` | `business_registration.tax_id` |
| `bank_account_name` | `bank_letter.account_holder_name` |
| `bank_routing_number` | `bank_letter.routing_number` |
| `owner_name` | `id_document.full_name` |
| `owner_address` | `id_document.address` |

Every application also carries a `submission_note`, sometimes empty, sometimes a genuine and
specific explanation for one field's discrepancy, sometimes a generic remark that explains
nothing. `derive_flags()` in `tools/build_corpus.py` is the single implementation of the rule that
turns (declared value, document value, submission_note) into one of three flags per field:

| flag | means |
|---|---|
| `match` | the declared value and the document value agree |
| `mismatch` | they disagree, and nothing in `submission_note` explains why |
| `mismatch_explained` | they disagree, **and** `submission_note` specifically and genuinely names *that* field's discrepancy -- not a generic note, not a note about a different field |

`verification_outcome` -- the historical `approved` / `denied` / `escalated` call the real
verification team reached -- is derived from the flags alone, never authored: any unexplained
mismatch on a banking-identity field (`bank_account_name` or `bank_routing_number`) is `denied`;
an unexplained mismatch confined to identity fields is `escalated`; no unexplained mismatch at all
is `approved`. This kit's model is never asked to reproduce this outcome -- see the guardrail in
`src/prompt.py` -- gold carries it only so a later step can show whether the model's flags would
plausibly have supported the team's real call.

## The trap, planted on purpose

**13 of the 36 applications (~36%, inside the product spec's 30-40% band) mismatch ONLY
`bank_routing_number`** -- every other of the seven fields matches cleanly, and
`submission_note` is either empty or a generic remark that never mentions banking. This is the
exact failure named in the product spec: *"a mismatched banking detail on an otherwise clean
application... a fraudulent application"*. A reader (model or baseline) that under-weighs a
single mismatched field because six others look clean, or that reads an unrelated note as if it
explains the banking mismatch, reproduces exactly the failure this kit exists to catch.

**This is a data-shape trap, not adversarial text.** Nothing in any field is written to deceive --
every value is exactly what it says, and no note claims something untrue. `derive_flags()` labels
gold at generation time and, independently, via `--verify`, re-checks every row against the
application record actually written to disk.

## What it cannot tell you

⚠︎ **This kit assumes every submitted verification document already arrives text-extractable.**
The business registration, bank letter and government ID blocks below are clean fields, standing
in for documents already OCR'd or otherwise extracted to text -- this kit does not parse images or
PDFs. A low-quality photo submission that OCRs poorly has no clean text for this kit to read, and
this kit has no way to notice that a document it was given is degraded rather than simply
mismatched. A real deployment needs a manual fallback for exactly that case.

⚠︎ **The trap denominator is a fixed count, not an independent draw.** 13 trap applications is
what a corpus of this scale supports honestly, chosen to land inside the spec's 30-40% band rather
than drawn independently per application (which can legitimately miss the band at this size). It
is reported as a raw count alongside the rate for exactly this reason -- see `evals/scoring.py`.

⚠︎ **Every application carries at most one pattern.** A real application can carry more than one
kind of discrepancy at once in more combinations than the five patterns here cover; this corpus
keeps to five named, legible patterns (`clean`, `banking_trap`, `explained_single`,
`escalated_nonbanking`, `denied_multi`) rather than sampling the full combinatorial space, so the
failure modes stay legible. See `tools/build_corpus.py`'s `PATTERN_COUNTS`.
