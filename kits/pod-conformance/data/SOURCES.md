# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every proof-of-delivery record from a
fixed seed (`SEED = 20260821`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260821` |
| dataset version | `pod-conformance-2026-08-21-55records` |
| licence | **MIT** — this repository's own licence |
| records | 55, in `data/corpus/*.txt`, 29,657 bytes |
| gold | 55 rows in `data/gold.jsonl` |
| carriers / shipments / sites | invented names and invented shipment numbers, with no link to a real carrier, consignee or delivery network |

## Why an invented set of delivery records, when real ones exist

**Because a real proof of delivery is not something this repo can publish either.** It names a real
carrier, a real consignee's site and a named driver's own words about a stop that happened, and it
usually carries a signature image belonging to a person. There is no public corpus of (delivery
record, true completeness) pairs, for the same reason no public corpus of bank statements or pay
stubs exists.

**No real carrier, consignee, freight brand or published logistics standard is named or reproduced
anywhere in this kit.** "Proof of delivery", "ordered quantity", "delivered quantity" and "condition
code" are ordinary receiving vocabulary; every carrier, site, shipment number and driver note here
was invented for this corpus.

## The mechanic: one call per record, ten fields

Each record states a shipment, a carrier, a receiving site, the delivery date, the timestamp of the
scan, the units ordered, the units actually scanned at the drop, a structured condition code, a
signature flag, and the driver's own free-text exception note. The model extracts ten fields —
everything except the receiving site, which no field maps to and which is therefore never sent —
including the one it has to decide: whether the delivery arrived as booked. See `src/prompt.py`.

## The planted ambiguity: completeness is structured data, and the prose disagrees with it

The eval this kit exists to run is whether a model **compares the two counts** or **reads the
driver's tone**. `N_AMBIGUOUS = 22` puts a note from the wrong register on exactly 40% of records:

- a delivery that is genuinely short, damaged or unassessed carrying a breezy note — "All good on
  my end. Left with the receiving clerk, no issues to report." — while the counts say otherwise;
- a delivery whose counts match exactly and whose condition code reads `undamaged` carrying an
  anxious one — "Sorry for the mix-up, had to leave it at the gate because the dock was full."

Gold's `delivery_complete` is **never** derived from the note. It is the comparison, run over the
same two quantities and the same condition code the document itself states:

```
complete  <=>  delivered_quantity == ordered_quantity  AND  condition_code == "undamaged"
```

`evals/check_labels.py` re-runs that comparison over every gold row before a run is allowed to
spend, and fails if any label disagrees with its own values. `tools/build_corpus.py::_verify()`
separately confirms every gold value is stated verbatim in the document it labels, and that every
`pod_timestamp` is a real instant sitting on its own `delivery_date` inside the delivery window.

**Equality is exact in both directions.** A shortfall is not complete, and neither is a surplus:
"at least the ordered quantity arrived" is the natural reading of the rule and it is the wrong one,
because a pallet more than the order says is still an order that did not arrive as booked. Three
records deliver *more* units than were ordered, on purpose, so that reading is measured rather than
assumed away.

## The composition is exact, then shuffled — not drawn per record

The sibling kits in this series draw each record's class from an independent coin. That is fine at
500 records and it is not fine at 55: **the first version of this generator asked for 40% ambiguity
and delivered 51%, and asked for a share of over-deliveries and delivered one.** A count 1.7
standard deviations off its own design is not a corpus property, it is sampling noise being
published as one. So each class here is a fixed **count**, shuffled by the seeded RNG. The corpus
is still deterministic and still byte-identical on every run; what changes is that the numbers on
the page are the numbers the design asked for.

The mix on this seed:

| | |
|---|---|
| complete | 28 |
| did not arrive as booked | 27 |
| — short | 11 |
| — counts match, condition code `damaged` | 7 |
| — counts match, condition code `unknown` | 4 |
| — **more** units delivered than ordered | 3 |
| — short **and** damaged | 2 |
| driver note from the contradicting register | 22 (40%) |
| incomplete **and** unsigned — the review flag | 10 |

## A defect in the free floor, found and fixed before anything was paid for

`evals/baseline.py` decides completeness from the exception note alone, and the gap between that
and a model is the number this kit publishes. That gap only means what it says if the floor
actually detects the register the note was written in. **It did not.** A keyword list containing
`"flagging"` fired on a breezy note reading *"nothing worth flagging"* — a negation — and
mis-registered four records. Two of those four were records the corpus had deliberately made
ambiguous, so the bug returned the **right answer for the wrong reason**, and the floor's error
count read 24 against a design of 22.

Both numbers look plausible, and a floor scoring slightly worse than designed looks like a floor
working. The fix was the keyword list, not the corpus (the anxious note is still caught on "mess"),
and the property is now **asserted for free** in `evals/check_labels.py`: every note template must
classify to the register it was authored in, before any run may spend.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` routes a record to an operations follow-up when the delivery did not
arrive as booked **and** no recipient signature is on file. A shortfall somebody signed for is
already documented and acknowledged; the same shortfall with no signature has nothing on file to
show the recipient was ever told.

⚠︎ **This is the kit's own simplification, not a real carrier's claims-intake policy.** No published
SLA, tariff or carrier liability rule was consulted, and none is reproduced. A real claims desk
weighs shipment value, commodity, the consignee's own receiving standard and the terms on the bill
of lading; this is two booleans, chosen because it is the smallest rule that is genuinely useful
and readable off one reply.

## What it cannot tell you

⚠︎ **This kit checks and routes only — it never files a claim, issues a credit or contacts a
carrier.** `delivery_complete` is an extracted field and `needs_review` is a routing signal;
nothing here disposes of anything.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real
receiving queue carries confusions this one does not attempt — a quantity stated in cartons on one
line and pallets on the other, one order arriving split across two stops, a re-delivery that
supersedes the first attempt, a condition code from a scan system with more than three values, or a
signature captured as an image with no structured flag at all. A model that clears this corpus has
cleared what this corpus tests, not every way a delivery exception can go wrong.
