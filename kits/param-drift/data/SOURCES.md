# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every parameter, every reading and every
gold label from a fixed seed (`SEED = 20260818`), so the corpus is byte-identical on every rebuild
and there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260818` |
| licence | **MIT** — this repository's own licence |
| parameters | 60, in `data/parameters.jsonl` — 20 per category x 3 categories |
| readings | 600 in `data/readings.csv` — 10 periods per parameter |
| gold | 60 rows in `data/labelled.jsonl` — drift/no-drift, trap, and the corrected value a historical analyst would have approved |
| formats | jsonl (parameters, gold), csv (readings) |

## Why an invented parameter set, when real ones exist

**Because a real one cannot be published at all.** A real configured-lead-time-vs-receipt-lag
comparison names a real supplier, a real committed schedule and a real safety margin sized around
a real demand history — exactly the material an operator will not let leave the building. There is
no public corpus of paired (configured value, observed rolling window, adjudicated correction) for
the same reason there is no public corpus of production alert histories or signed supplier
agreements: the interesting cases are exactly the ones nobody can publish.

**Nothing in here refers to a real company.** Supplier, site and channel names, SKU numbers and
every reading are invented; no row here states a real commercial term.

## The job is generic; the flavour is not

This kit's actual job — compare a configured operating constant against a system's own observed
behaviour over a rolling window, and flag a mismatch with a proposed corrected value attached —
applies to any configured constant a system relies on: a lead time, a safety margin, a staffing
ratio, an SLA threshold, a reorder point. This corpus happens to flavour the three categories as a
supplier lead time, a demand-variability buffer and a service target across a synthetic
replenishment scenario, because that gives three genuinely independent correction formulas
(mean-based, std-based, mean-based-again-but-bounded) to exercise in one corpus. Point
`tools/build_corpus.py` at your own parameter shape and your own categories and the pipeline —
`src/aggregate.py`, `src/formulas.py`, `src/prompt.py` — does not change.

## Three categories, three correction formulas, never the same one twice

| category | configured value | observed window | correction formula |
|---|---|---|---|
| `lead_time` | a duration (days) | per-period receipt lag | whole-window mean |
| `safety_margin` | a buffer (units) | per-period demand | `1.65 x` the whole-window sample std |
| `service_target` | a rate/threshold (pct) | per-period achieved rate | whole-window mean |

`Z_SAFETY = 1.65` is an assumed 95%-service constant, stated once in `src/formulas.py`, the same
way `change-impact`'s `EXPEDITE_RATE_PER_UNIT_DAY` states an invented rush-fee rate — a real
deployment supplies its own target and its own z.

## Four scenarios ("traps") per category, planted so the free floor and real judgement are worth telling apart

| trap | what it is | count/category |
|---|---|---|
| `clean_drift` | a real, sustained mismatch. Easy: both the floor and a careful reader should catch it. | 5 |
| `clean_hold` | configured value already matches observed behaviour. Easy the other way. | 7 |
| `one_off_spike` | ONE anomalous reading, logged with a one-time-event note, in an otherwise matched window. A naive mean/std threshold can be fooled into flagging it. | 4 |
| `slow_creep` | a steady, one-directional drift across the whole window that ends well away from configured but keeps the whole-window average looking mild. | 4 |

27 of 60 parameters are labelled `drift` (45%), 33 `no_drift` (55%) — a deliberately moderate split,
not the 8%-page imbalance `ops-triage`'s corpus uses; this kit's eval intent calls for precision
AND recall to both be legible, which a heavily skewed set would obscure.

## The gold value is never computed by the formula it is measured against

`tools/build_corpus.py` decides a TRUE underlying value at generation time — known only to the
generator — and samples the window's readings around it with realistic noise. The gold corrected
value IS that true value. `src/formulas.py::corrected_value`, which the pipeline actually runs, is
computed later from the noisy OBSERVED window alone, with no access to the true value the generator
used. How close the two land is therefore a real, measured question: a generator that imported
`src/formulas.py` to label its own gold would make "value agreement" tautological, scoring 100% on
every drift case by construction and testing nothing. This corpus deliberately does not do that —
see `README.md`'s finding 2 for what that measurement actually found.

## What the floor and the model cannot see, and why value agreement is weaker on `safety_margin`

⚠︎ **Estimating a standard deviation from 10 readings carries far more sampling noise than
estimating a mean does.** The sample-std estimator's own relative standard deviation from a window
this size is on the order of 20-25%, purely from sampling — a structural property of the method,
not a defect in the model or the floor. This is measured, not asserted: `safety_margin`'s value
agreement (42.9%) is well below `lead_time`'s (66.7%) and `service_target`'s (100%), and the
category's threshold-based floor decision is noisier for the same reason — see `evals/baseline.py`'s
own per-category output.

⚠︎ **The trend fact tracks the window's mean, not its spread.** `src/aggregate.py::trend` compares
first-half vs second-half MEAN. A `safety_margin` parameter whose true demand *variability* is
creeping — rather than its average level — produces no material change in that fact, so neither the
floor nor a reader relying on it sees the real signal. `PD-0037` in the real run is exactly this
case: variance widens steadily across the window while the mean stays flat, and both the floor and
the model held it.

⚠︎ **An invented corpus contains the traps we thought to plant and no others.** A real deployment's
parameters carry drift shapes this one does not attempt — two parameters moving together, a
seasonal pattern mistaken for drift, a window with missing periods. A checker that clears this
corpus has cleared what this corpus tests, not every way a real parameter can misbehave.

⚠︎ **At most one window per parameter.** A real monitoring system re-cuts the rolling window every
cycle and would see a `one_off_spike` age out of the window over time; this corpus plants exactly
one static ten-period snapshot per parameter.
