# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every usage-to-invoice reconciliation
record from a fixed seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and
there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `usage-variance-2026-08-22-55records` |
| licence | **MIT** — this repository's own licence |
| records | 55, in `data/corpus/*.txt`, 32,056 bytes |
| gold | 55 rows in `data/gold.jsonl` |
| line ids / rating domains / analyst notes | invented identifiers and invented mediation-partition names, with no link to a real carrier, tariff, interconnect agreement or customer |

## Why an invented set of reconciliation records, when real ones exist

**Because a real usage-to-invoice reconciliation record is not something this repo can publish
either.** It carries a real customer's account, a real service line and a billing analyst's own
note about that specific line, and behind it sits the call-detail traffic for one subscriber. There
is no public corpus of (mediated usage, invoiced quantity, correct variance cause) triples, for the
same reason there is no public corpus of bank statements or proof-of-delivery records.

**No real carrier, real mediation platform, real filed tariff or real interconnect settlement rule
is named or reproduced anywhere in this kit.** "Mediated usage", "unrated usage", "suspense
bucket", "duplicate suspects", "prior period" and "billing increment" are ordinary telecoms billing
vocabulary; every line id, rating-domain name, quantity and analyst note here was invented for this
corpus.

## The mechanic: one call per reconciliation record, eleven fields

Each record states an invoice line, the mediation partition it came out of, the service it bills,
the billing period, five quantities, whether the invoice has been issued, and the billing analyst's
own free-text note. The model extracts eleven fields — everything except the rating domain, which
no field maps to and which is therefore never sent — including the one it has to decide: **why**
the invoiced quantity differs from what should have been billed. See `src/prompt.py`.

## The arithmetic

The mediated total for a line and period is four **disjoint** parts:

```
mediated = rated + unrated + prior_period + confirmed_duplicates
```

| part | what it is | billable this period? |
|---|---|---|
| rated | correctly rated traffic | yes |
| unrated | failed rating, sitting in suspense | **yes** — it is still this period's usage and is still owed |
| prior_period | arrived after the collection cutoff, belongs to the PREVIOUS period | no |
| confirmed_duplicates | the same session counted twice, confirmed by review | no |

so

```
billable = mediated - prior_period - confirmed_duplicates      (unrated STAYS in)
expected = round_up(billable, increment(service_type))
gap      = invoiced - expected
```

## The billing increment is a property of the service

| service | unit | increment | why it matters |
|---|---|---|---|
| voice | seconds | 60 | whole-minute rounding, so a 59-second gap is not a variance |
| data | KB | 1024 | whole-megabyte rounding |
| sms | messages | **1** | **no rounding tolerance at all** — a one-message gap IS a variance |

One tolerance applied to all three services is wrong in both directions at once: it forgives real
SMS variances and invents voice ones. **13 of these 55 records are SMS lines and none of them can
carry a `rounding` label** — `evals/check_labels.py` asserts that directly, and separately asserts
the boundary itself on every non-SMS row (a gap of one unit under the increment must classify as
rounding; a gap of exactly the increment must not).

## The priority order, and why each step sits where it does

```
1. gap == 0                                        -> none
2. abs(gap) < increment                            -> rounding
3. gap < 0 and matches unrated_quantity            -> unrated_usage
4. gap > 0 and matches confirmed_duplicate_quantity -> duplicate_records
5. gap > 0 and matches prior_period_quantity       -> late_records
6. otherwise                                       -> unexplained
```

**Rounding is checked before any cause is named.** A gap smaller than one increment is
indistinguishable from a small missed block, so naming a cause for it is a guess dressed as a
finding.

The rule lives in one function — `tools/build_corpus.py::classify()` and
`src/extract.py::classify()` are the same six-branch logic, used to write gold and to re-derive it
from the model's own reply — and is stated to the model by `src/prompt.py`, so the kit cannot drift
about what a variance cause means.

## The four planted decoys

Three of them are **numeric**, which is what makes this corpus harder than a note-versus-values
one: the loud number on the page is the wrong number, and reaching for it produces a confident,
well-formed, wrong answer.

| | |
|---|---|
| **A. prior-period usage that is correctly excluded** | **37 records state a non-zero late-arrival figure and only 8 of them are the `late_records` case.** 7 of them are exactly correct invoices. Reading "late CDRs present" as "variance" fails all 7 |
| **B. duplicate suspects that are not duplicates** | every record states BOTH the raw figure de-duplication flagged AND the figure review confirmed. **44 of 55 flag more than review confirmed, and on 22 of those review confirmed NONE of it** — two genuinely distinct sessions that looked alike. Subtracting suspects invents a gap |
| **C. unrated usage that was already re-rated and billed** | unrated stays inside billable, so **8 records carry a non-zero suspense bucket on a perfectly correct invoice**. Treating a suspense figure as automatically a shortfall fails all 8 |
| **D. an analyst note naming the wrong cause** | `N_AMBIGUOUS = 22`, exactly 40% — a note that names duplicates on a rounding line, late records on a duplicate line, and so on |

Gold's `variance_cause` is **never** derived from the note. It is the arithmetic, run over the same
quantities the record itself states.

`evals/check_labels.py` re-runs that arithmetic over every gold row before a run is allowed to
spend, and fails if any label disagrees with its own values — and separately asserts that every
note template in `tools/build_corpus.py` classifies to the register it was written as, against the
free floor's own keyword table, **and that no template matches two registers**. That second
assertion exists because this floor is a six-way classifier rather than a binary one: a template
matching two registers would make the floor's answer depend on the order of its own keyword table
rather than on the note, which is a silent dependence nobody would see in a score. A sibling kit
earlier in this series shipped a keyword that fired on a negation inside a calm note and
mis-registered four records for days; that check is written into this kit's gate from the start.

## The composition is exact, then shuffled — not drawn per record

Several sibling kits in this series draw each record's class from an independent coin, which is
fine at 500 records and is not fine at 55 — a first version of an earlier kit's generator asked for
40% ambiguity and delivered 51%. So each class here is a fixed **count**, shuffled by the seeded
RNG. The corpus is still deterministic and still byte-identical on every run; what changes is that
the numbers on the page are the numbers the design asked for.

The mix on this seed:

| | |
|---|---|
| `none` — the invoice is right | 16 |
| `rounding` — a sub-increment gap, explained | 8 |
| `unrated_usage` — the suspense bucket never reached the invoice (under-billed) | 11 |
| `duplicate_records` — confirmed duplicates were charged for (over-billed) | 8 |
| `late_records` — the previous period's arrivals were charged here (over-billed) | 8 |
| `unexplained` — a real gap that ties back to none of the three blocks | 4 |
| voice / data / sms | 21 / 21 / 13 |
| analyst note naming a cause the arithmetic does not support | 22 (40%) |
| over-billed **and** already issued — the credit flag | 8 |

`rounding` cannot exist on an SMS line, so the generator **swaps** service types rather than
redrawing them when the deal puts one there — a redraw would move the service totals off their
exact counts, which is the whole thing exact-then-shuffle exists to protect.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises a customer credit when the variance **over**-billed —
`duplicate_records` or `late_records` — **and** the invoice has already been issued. Either variance
on a draft can simply be corrected before it goes out; the same variance on an issued invoice means
the customer has paid for usage they do not owe.

`unrated_usage` deliberately does **not** fire it. That is under-billing: real revenue leakage, and
a real revenue-assurance team cares about it, but nobody is owed money and no customer is waiting.
Splitting the two is the whole reason this rule is a separate function from `classify()`.

⚠︎ **This is the kit's own simplification, not a real carrier's billing-adjustment policy.** No
published tariff, settlement rule, regulatory requirement or operator's own credit procedure was
consulted, and none is reproduced. A real billing desk weighs the dollar size of the credit, the
dispute window, and whether the line sits inside a contracted tolerance; this is one enum test and
one boolean, chosen because it is the smallest rule that is genuinely useful and readable off one
reply.

## What it cannot tell you

⚠︎ **This kit reconciles and routes only — it never issues a credit, reverses a charge, re-rates a
suspense bucket or contacts a customer.** `variance_cause` is an extracted field and `needs_credit`
is a routing signal; nothing here disposes of anything.

⚠︎ **The quantities arrive pre-aggregated.** A real reconciliation starts from millions of raw
usage records and does the aggregation itself; this corpus hands the model five totals somebody
else already computed. Everything this kit measures is downstream of the step most likely to be
wrong in production.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real billing
queue carries confusions this one does not attempt — a mid-cycle plan change, proration across a
tariff switch, a wrong rate applied to correctly-counted usage (this kit reconciles QUANTITY, not
amount), roaming records settled in another operator's units, or a bundled allowance that changes
what "billable" means. A model that clears this corpus has cleared what this corpus tests, not
every way a usage-to-invoice reconciliation can go wrong.
