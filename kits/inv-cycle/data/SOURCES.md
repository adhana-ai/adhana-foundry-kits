# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every variance event, its full
transaction history log and its gold cause from a fixed seed (`SEED = 20260819`), so the corpus is
byte-identical on every rebuild and there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260819` |
| licence | **MIT** — this repository's own licence |
| events | 36, in `data/events.jsonl` — each carrying one item/location/period, its variance and a 4-8 line transaction history log |
| gold | 36 rows in `data/gold.jsonl` — every event's derived cause, citation line index and confirmed note |
| formats | jsonl (events, gold) |

## Why an invented cycle-count corpus, when real ones exist

**Because a real one cannot be published at all.** A real cycle-count variance log names real
SKUs, real store or warehouse codes and real transaction volumes — exactly the material an
inventory-control team will not let leave the building. There is no public corpus of paired
(transaction history log, variance, adjudicated root cause) for the same reason there is no public
corpus of internal receiving or transfer logs.

**Nothing in here refers to a real company.** Every location code, SKU, product category and log
line is invented; no row here states a real commercial figure.

## The job is generic; the flavour is not

This kit's actual job — read one item/location's own transaction history, decide whether it
supports a specific, traceable explanation for a physical-count variance, and say so honestly
when it doesn't — applies to any inventory system that logs receiving, transfers, scans and
adjustments against a location. This corpus flavours it as a retail/warehouse cycle-count program
in dollars-free unit counts, across synthetic product categories, because that is the scenario the
kit's originating use case names. Point `tools/build_corpus.py` at your own transaction types and
your own item master and the pipeline — `src/segment.py`, `src/pack.py`, `src/prompt.py` — does
not change.

## Five causes, one of them deliberately planted two ways

| cause | what it is | how the log evidences it |
|---|---|---|
| `mis_receipt` | a receiving correction was logged but never applied to on-hand | a flagged `receiving_correction` log line, linked to the original receiving line's PO |
| `unrecorded_transfer` | the variance lines up with unlogged activity at another location | a flagged `counterpart_activity` log line naming the other location |
| `uom_error` | eaches and cases were mixed up for this item | a flagged `uom_note` log line **and** variance_qty is a clean multiple of the item's case-pack size |
| `unscanned_movement` | more moved than the scan/pick log shows | the log's own arithmetic doesn't reconcile with variance_qty, and at least one scan line exists |
| `unresolved` | none of the above cleanly fits | no flag fires and no scan line exists to fall back on |

**The trap, planted on purpose.** ~44% of `unrecorded_transfer` events (4 of 9) also have a
variance_qty that is a clean case-pack multiple — the surface signal `uom_error` looks for. Gold
still says `unrecorded_transfer` for these, because `uom_error` requires the specific
`uom_note`-flagged evidence line, not merely a divisible number, and `src/segment.py::classify()`
checks the `counterpart_activity` flag before it ever checks the case-pack arithmetic. A reader —
model or person — who pattern-matches "divides evenly by 12, must be a UOM mix-up" without reading
the actual log produces exactly this kit's named failure mode:
`evals/scoring.py`'s `uom_transfer_confusion` metric counts it directly, denominator = trap cases
only. `evals/baseline.py`'s dumb rule gets **all four** of these trap cases wrong by construction —
see its own docstring.

## The gold cause is never inferred by hand

`tools/build_corpus.py` constructs each event's transaction log to carry the structural evidence a
real one would (a flagged line, a chosen quantity, a chosen direction) — it never writes a
`true_cause` string directly into gold. Once an event is assembled, `src/segment.py::classify()`
is the only thing that decides its cause and citation, from the log and variance_qty alone; the
same function grades a live model's citations in `evals/scoring.py`. `tools/verify_gold.py`
re-runs `classify()` over the finished `data/gold.jsonl` and fails loudly on any disagreement —
run it any time the corpus changes.

## What this corpus does not test

- **One event per item/location/period, not a rolling history.** A real deployment would see the
  same item recur cycle over cycle, sometimes still unresolved from last time; this corpus judges
  every event independently.
- **One planted cause per event.** A real variance can have two compounding causes at once; this
  corpus always plants exactly one (or none, for `unresolved`).
- **A cause outside the five-member vocabulary.** A real cycle-count program will eventually name
  a cause this kit's fixed list does not carry — a damaged-goods write-off never logged, a vendor
  shorted a case — extending it is a `src/rubric.py` change plus new template evidence in
  `tools/build_corpus.py`, not a prompt tweak alone.
- **Transaction history that is incomplete by design, not just unlucky.** This kit assumes
  receiving, transfers and scans are captured completely enough to reconstruct a variance's cause.
  A store still running manual transfer logs on paper leaves gaps this corpus never models — see
  the open risk noted in `README.md`.
