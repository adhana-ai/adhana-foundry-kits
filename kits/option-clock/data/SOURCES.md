# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every rights-register snapshot from a
fixed seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `option-clock-2026-08-22-50registers` |
| licence | **MIT** — this repository's own licence |
| registers | 50, in `data/corpus/*.txt`, 50,619 bytes |
| gold | 50 rows in `data/gold.jsonl` |
| counting rulebook | `data/rulebook.json` — **written for this kit**, see the warning below |
| properties / parties / references / notes | invented titles, invented companies, invented register and payment references, invented clerk notes, with no link to any real work, company, person or file |

## ⚠︎ The counting rulebook is illustrative and is NOT an authority

**`data/rulebook.json` was authored for this kit.** It reproduces **no** option agreement, **no**
standard form, **no** rights-management system's own logic, **no** guild, union or trade-body
schedule and **no** statute. Nothing in it was copied from, derived from, or checked against any
such document, because none was consulted.

It is a small, deliberately readable construction whose only job is to make the *counting shape*
measurable: what starts the clock, what perfects an extension, how extensions stack, how months are
added, and how far ahead "about to lapse" looks. Several of its simplifications are visibly not how
a real option works — most obviously that every extension in a chain is the same length, and that a
single 45-day window applies to every property regardless of what is at stake behind it.

**The real authority for any option is the executed agreement and the lawyer who reads it.** This
kit proposes a worklist with the count that produced it and names what it could not determine. It
never exercises, renews, lapses, releases or clears anything, and nothing in it writes, dispatches
or files anything. That sentence is on the kit's own UI, above the answer, and not only here.

**And it watches nothing.** It reads ONE snapshot that somebody else assembled, on the date that
snapshot states. There is no poller, no scheduler, no subscription, no queue and no state between
documents. Nothing in this kit runs unattended.

**Every name in the corpus is invented.** No real work, studio, streaming service, publisher,
distributor, guild, union, agency, label, trade body, court, docket, production or person is named
anywhere in this kit. Property titles, rights holders, grantees, agents, counsel, escrow agents and
co-financiers were all made up for it.

## Why an invented set of registers, when real ones exist

**Because a real rights register is not something this repo can publish either.** It names a real
author's work, a real company's money, a named clerk's own remark and a live commercial position on
a property that has not been announced. There is no public corpus of (rights register, correct
status) pairs, for the same reason there is no public corpus of bank statements or cleaning
certificates.

Generating it also makes the label mechanical: gold's `status` is the rulebook count run over the
same values the register itself states, never somebody's reading of the status column.

## The mechanic: one call per register, seventeen fields

Each register states the property, the rights holder, the grantee, the date the snapshot is current
as at, when the option was granted, what starts its clock, the triggering event and whether it has
occurred, the initial term, each extension the agreement grants with what perfects it and what the
file records against it, the status the register itself carries, and the rights clerk's own remark.
The model extracts seventeen fields — everything except the filing-history block, which no field
maps to and which is therefore never sent — including the two it has to count: the expiry date and
the status. See `src/prompt.py`.

**The rulebook is sent with every call.** What starts a clock and what perfects an extension are
facts about a rulebook, and a model cannot apply a rulebook it has never been shown.
`src/prompt.py::rulebook_block()` renders `data/rulebook.json` into the prompt rather than restating
it in prose, so the model's instructions and the gold labels cannot drift apart about the same
count. Measured on the worked example: 1,039 of 3,292 input tokens (32%) are the rulebook.

## The model reads. The code counts.

**The answer this kit publishes is the pure-code count, not the model's own answer.** A due date is
arithmetic, and arithmetic done in prose is arithmetic nobody can check. The model returns
`expiry_date` and `status` as fields anyway, and the gap between its answer and the code's is this
kit's no-gold consistency diagnostic — the one figure a forker can compute on registers nobody has
labelled.

That is not a theoretical distinction here. On the scored run **the model's own stated status was
wrong on one register of fifty**, `ROR-0033`: it clamped a 29th-of-the-month start into February
correctly and then added the extension's 6 months instead of the initial term's 18, put the expiry a
year early at `2026-02-28`, and called an option with six months left `lapsed`. The register's own
status line said `live` and the clerk's note read *"Chased the file twice and I am not confident the
dates on it are settled."* — so the wrong answer had a worried note beside it and would have read as
a catch. **Left to the model that is a false alarm.** The code counted `2027-02-28` and `live`, and
the consistency diagnostic named the disagreement using no labels at all.

⚠︎ **And it is not reproducible.** The same register re-asked once after the run
(`results/example-ROR-0033.json`) came back with `2027-02-28` and `live`. Same prompt, same tier,
same document, different arithmetic. That is the strongest single argument on this page for not
publishing a model's own count.

## The rule, and the order a reader gets wrong

```
status(register_as_of, clock_basis, trigger_status, option_granted_date, trigger_date,
       initial_term_months, extension_months_each, extensions_perfected):
    1. WHAT STARTS THE CLOCK
         triggering_event, not occurred        -> not_determinable   (nothing to count from)
         grant_date, two entries disagreeing   -> not_determinable   (do not break the tie)
         otherwise                             -> the trigger date, or the grant date
    2. WHICH EXTENSIONS COUNT
         payment-controlled: a payment reference AND a payment date must both be recorded
         notice-controlled:  notice must be served on the GRANTOR OF RECORD
         anything else recorded as exercised   -> does not stack
    3. ADD THE MONTHS, consecutively from the clock start, in one calendar step,
       clamped to the end of a short month
    4. COMPARE against the as-of date and the 45-day window
         expiry <= as_of                       -> lapsed
         as_of < expiry <= as_of + 45          -> lapsing
         expiry >  as_of + 45                  -> live
```

Five things about that count are stated to the model in full, because each is a reading a careless
reader falls into on its own — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **"recorded: exercised" is not a perfected extension** | the entry is a clerk's; the payment or the notice is the act. Count the entry and the option reads `live`; refuse to count it and it is lapsed or lapsing — asserted directly in `evals/check_labels.py`, not hoped for | **9 registers** |
| **a clock that has not started is not a long time left** | a triggering-event option whose event has not happened is `not_determinable`. Reading it as `live` removes a row from the worklist and looks like good news | **5 registers** |
| **a contradicted date is not settled** | two entries disagreeing about a grant date the clock runs from settles nothing, and the rule explicitly forbids breaking the tie | **4 registers** |
| **…but a contradiction only blocks the date the clock RUNS FROM** | the same two disagreeing entries on a register whose clock runs from a triggering event that has occurred change nothing. Flagging it is a **false alarm** | **3 registers** |
| **the register's own status line is wrong in both directions** | 25 registers are carried as `live` and are not; 4 are carried as `lapsed` and are in fact live | **29 registers** |

The rule lives in one function — `src/rulebook.py::decide()` — used to write gold, stated to the
model by `src/prompt.py`, and re-run over the model's own reply by `src/extract.py` to produce the
published answer. Three readers, one definition, so the corpus, the prompt and the answer cannot
drift about what `lapsing` means.

## The planted ambiguity: the status is a count, and the clerk's note disagrees with it

`N_AMBIGUOUS = 20` puts a clerk's note from the wrong register on exactly 40% of files:

- an option that has already lapsed, or cannot be dated at all, carrying a relaxed note — *"Clean
  file, nothing for the desk to do here as far as I can see."*;
- an option with a year and a half to run, carrying a note that reads like a problem — *"This one
  looks tight to me — worth a second pair of eyes before the next sweep."*

Gold's `status` is **never** derived from the note, and never from the register's own status line.
It is the count, run over the same values the register itself states.

`evals/check_labels.py` re-runs that count over every gold row before a run is allowed to spend, and
fails if any label disagrees with its own values — and separately asserts that every note template
classifies to the register it was written as, against the free floor's own keyword list, before
anything may spend. A sibling kit earlier in this series shipped a keyword that fired on a negation
inside a relaxed note and mis-registered four records for days; that check is written into this
kit's gate from the start rather than found live.

## The composition is exact, then shuffled — not drawn per register

Each of the ten buckets is a fixed **count**, shuffled by the seeded RNG, and every constructor is
asserted against the rulebook at build time — a constructor that quietly stops producing its own
bucket is exactly the defect an exact composition exists to prevent.

| | |
|---|---|
| `live` | 17 |
| — ordinary, register agrees | 10 |
| — carried as **lapsed** and in fact live, on a properly perfected extension | 4 |
| — carrying an **immaterial** grant-date disagreement (the false-alarm trap) | 3 |
| `lapsed` | 14 |
| — ordinary, register agrees | 8 |
| — still carried as `live` | 3 |
| — an extension recorded as exercised that was never perfected | 3 |
| `lapsing`, inside the 45-day window | 10 |
| — plain, and the register has no word for it | 4 |
| — an extension recorded as exercised that was never perfected | 6 |
| `not_determinable` | 9 |
| — a triggering event that has not occurred | 5 |
| — two entries disagreeing about a grant date the clock runs from | 4 |
| clerk note from the contradicting register | 20 (40%) |
| registers whose own status line disagrees with the count | 29 |
| not live **and** still carried as live — the escalation flag | 25 |
| expiries landing on the short-month clause (a clamped day-of-month) | 6 |

**18 of the 50 registers say exactly what they mean**, and the register's own status line agrees
with the count on 21 of them. That is deliberate. A corpus where the file is wrong most of the time
is a corpus built to flatter the model; the interesting claim is that the count finds the minority
the register gets wrong **without crying wolf over the majority it gets right**.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises an escalation when the counted status is anything other than
`live` **and** the register still carries itself as `live`. An option the register already shows as
lapsed is a known loss — somebody has typed the bad news into the file and the desk can see it. The
same count on a register still carrying `live` is the one nobody is looking at: it is on no report,
it is in nobody's diary, and it will be found when somebody tries to exercise. `not_determinable`
counts here too — treating a record nobody can date as a pass is the one thing a monitoring queue
must never do.

Note what that does with the decoy, because it looks like a contradiction and is not.
`register_status` is never an input to the **count** — the count is arithmetic and a status column
is not evidence about arithmetic. It **is** an input to the **routing**, because what the desk
currently believes is exactly what decides whether this row is news.

⚠︎ **This is the kit's own simplification, not a rights desk's real escalation policy.** No
company's procedure was consulted, and none is reproduced. A real desk weighs what the property is
worth, whether anybody still wants it, whether the counterparty would grant a fresh option anyway,
and who has authority to spend the exercise money.

## What it cannot tell you

⚠︎ **This kit reads and proposes only — it never exercises, renews, lapses or releases anything,
and it never contacts anybody.** `status` is a count and `escalate_now` is a routing signal; nothing
here disposes of anything.

⚠︎ **It watches nothing.** "Monitoring" here is one snapshot, read once, on demand. There is no
schedule, no poller, no subscription, no alert and no state between documents. If your registers
change, somebody else has to hand this kit the new snapshot.

⚠︎ **A run that scores perfectly has agreed with `data/rulebook.json`, which is a much smaller claim
than being right about a real option.** The graders measure whether the run applied the shipped
rulebook. They cannot measure whether the rulebook is correct, because the rulebook is this kit's
own construction.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real rights
book carries confusions this one does not attempt — an option chain with extensions of different
lengths, a term stated in years or in "the later of" two dates, a notice served late rather than on
the wrong party, a payment made in the wrong amount or to the wrong account, a side letter that
varies the agreement without appearing on the register, a property under two overlapping options,
and a register whose as-of date is itself stale. A model that clears this corpus has cleared what
this corpus tests, not every way an option clock can be misread.
