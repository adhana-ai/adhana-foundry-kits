# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every commission claim record from a
fixed seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `commission-audit-2026-08-22-55claims` |
| licence | **MIT** — this repository's own licence |
| records | 55, in `data/corpus/*.txt`, 39,070 bytes |
| gold | 55 rows in `data/gold.jsonl` |
| claims / confirmations / properties | invented identifiers and invented property names, with no link to a real booking channel, hotel, agreement or guest |

## No channel is named, and no guest exists

**The booking channel is never named anywhere in this kit** — not in the corpus, not in the field
schema, not in the prompt, not on any published figure. `booking_source` is an enum whose "came
through the channel that issued this invoice" value is the literal token `channel`. A brand name
in a corpus about disputed money is a claim about a real company's invoicing, and this repository
does not make one.

**There is no guest in this corpus at all.** A real folio names a guest, an address and a card;
none of that is needed to decide whether a commission is owed, so none of it is here. The record
carries a confirmation number, a folio status and money.

## Why an invented set of claim records, when real ones exist

**Because a real commission invoice line joined to a real folio is not something this repo can
publish either.** It names a real property's revenue, a real channel's contracted percentage and a
real reservation. There is no public corpus of (commission claim, correctly-owed-amount) pairs,
for the same reason there is no public corpus of bank statements or proof-of-delivery records.

**No real booking channel, real distribution agreement or real published commission schedule is
named or reproduced anywhere in this kit.** "Folio", "room revenue", "commissionable base",
"cancellation penalty" and "commission rate" are ordinary hotel-accounting vocabulary; every claim
id, confirmation number, property name and reviewer note here was invented for this corpus.

## The mechanic: one call per claim line, fourteen fields

Each record is **one line of a channel's commission invoice, joined to the property's own folio
record for the booking it claims against**. It states the claim id, the property, the confirmation
number, what the folio says happened, how the booking actually reached the property, the room
revenue and any refund, the taxes and fees beside them, any cancellation penalty charged, the
contracted percentage, the amount claimed, whether the stay was already commissioned, whether the
invoice has been paid, and the property reviewer's own free-text note. The model extracts fourteen
fields — everything except the property, which no field maps to and which is therefore never sent
— including the one it has to decide: whether the commission claimed is what is actually owed.
See `src/prompt.py`.

## The rule, and the priority order a reader doing arithmetic first gets wrong

```
owed(source, already, status, room_revenue, refunded, penalty, rate):
    source is not 'channel'            -> 0.00        (checked FIRST, before any arithmetic)
    already commissioned               -> 0.00        (checked SECOND)
    status is stayed or rebooked       -> base = room_revenue - refunded
    status is cancelled or no_show     -> base = penalty charged
    non-room charges                   -> NEVER in the base, in any branch
    base <= 0                          -> 0.00
    otherwise                          -> round(base * rate / 100, 2)
```

Five things about that rule are stated to the model in full, because each is a reading a model —
or a person — falls into on its own:

| | |
|---|---|
| **the booking source outranks everything** | a stay the folio shows arrived direct, through a corporate GDS or as a walk-in owes this channel nothing, however real the stay and however tidy the arithmetic. **5 of these 55 records are exactly that**, and every one of them carries a perfectly correct multiplication |
| **nothing is owed twice** | **4 records** are already commissioned on a previous invoice; every other value on the line is right |
| **taxes and fees are never in the base** | **6 records** claim commission on the folio total. The tax line sits directly beside room revenue, which is what makes it the commonest bad claim there is |
| **a cancellation is not automatically zero** | **9 records** are a cancellation or no-show with a penalty actually charged, and commission IS owed — on the penalty. **5 of them are correct claims**, so a reader who stops at "the guest did not stay" gets those five backwards |
| **a rebooked reservation is a stay** | **5 records** moved to a new confirmation number and the guest stayed. They are commissionable on room revenue exactly as a plain stay is |

The rule lives in one function — `tools/build_corpus.py::owed_commission()` and
`src/extract.py::owed_commission()` are the same five-branch logic, used to write gold and to
re-derive it from the model's own reply — and is stated to the model by `src/prompt.py`, so the
kit cannot drift about what "owed" means.

## The planted ambiguity: validity is folio arithmetic, and the note disagrees with it

`N_AMBIGUOUS = 22` puts a property reviewer's note from the wrong register on exactly 40% of
records:

- a genuinely bad claim carrying an accepting note — "Folio matches the claim, no action needed."
  — while the folio's own numbers say otherwise;
- a claim that is exactly right carrying a note that reads like a dispute — "Something looked off
  against the folio on this line, revisit before settlement."

Gold's `claim_valid` is **never** derived from the note. It is the computation, run over the same
values the record itself states.

`evals/check_labels.py` re-runs that computation over every gold row before a run is allowed to
spend, and fails if any label disagrees with its own values — and separately asserts that every
note template in `tools/build_corpus.py` classifies to the register it was written as, against the
free floor's own keyword list, before anything may spend. A sibling kit earlier in this series
shipped a keyword that fired on a negation inside an accepting note and mis-registered four
records for days; that check is written into this kit's gate from the start rather than found live.

## The composition is exact, then shuffled — not drawn per record

Each class here is a fixed **count**, shuffled by the seeded RNG, rather than drawn per record from
an independent coin. At 55 records a per-record draw delivers a mix a standard deviation or two off
its own design, and the numbers on the page then describe sampling noise rather than the corpus.

The mix on this seed:

| | |
|---|---|
| valid claims — claimed equals owed | 28 |
| — a plain channel stay, commission on room revenue | 10 |
| — a **rebooked** reservation, commissionable as a stay | 5 |
| — a **cancellation inside the penalty window**, commission owed on the penalty | 5 |
| — a **no-show with a penalty charged**, same | 4 |
| — a **partly refunded stay**, claimed correctly on the NET revenue | 4 |
| invalid claims — claimed is not what is owed | 27 |
| — commission computed on the folio total, **taxes and fees in the base** | 6 |
| — a claim on a booking that **came through a different channel** | 5 |
| — a partly refunded stay claimed on **gross** room revenue | 5 |
| — a stay **already commissioned** on a previous invoice | 4 |
| — a cancellation with **no penalty charged**, commission claimed anyway | 4 |
| — a **percentage other than the contracted one** applied | 3 |
| reviewer note from the contradicting register | 22 (40%) |
| invalid **and** the invoice is already paid — the recovery flag | 16 |

⚑ **Every allowed enum value actually occurs.** `tools/build_corpus.py::_verify()` and
`evals/check_labels.py` both assert it. A first version of the generator drew the non-channel
booking source per record and left `walk_in` unused on this seed — an allowed value no record
states is a value the run never measures, and finding that out from the published counts is too
late. The three non-channel sources are now dealt round-robin.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` routes a claim for a recovery claim when the commission claimed is not
what is owed **and** the invoice has already been paid. A bad line on an unpaid invoice can simply
be short-paid before settlement; the same line on an invoice already paid means the property is out
of pocket and has to raise a recovery claim against the channel.

⚠︎ **This is the kit's own simplification, not a real property's dispute policy.** No booking
channel's published dispute procedure, no signed distribution agreement and no property's own
recovery threshold was consulted, and none is reproduced. A real desk weighs the dollar size of the
variance, whether the channel's dispute window is still open, and the cost of raising a claim at
all; this is two booleans, chosen because it is the smallest rule that is genuinely useful and
readable off one reply.

## What it cannot tell you

⚠︎ **This kit checks and routes only — it never short-pays an invoice, raises a dispute or
contacts a channel.** `claim_valid` is an extracted field and `needs_recovery` is a routing signal;
nothing here disposes of anything.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real
commission invoice carries confusions this one does not attempt — a stay spanning a month boundary
billed across two invoices, a rate that changed mid-contract, a group block where the channel
claims on the whole block, a currency conversion between the channel's invoice and the property's
folio, or a single confirmation number covering several rooms on separate folios. A model that
clears this corpus has cleared what this corpus tests, not every way a commission claim can be
wrong.

⚠︎ **One claim, one folio, already joined.** The hardest part of this problem in production is
finding the folio at all — matching a channel's confirmation number against a property system that
renumbered it, or against a rebooked reservation that carries a different number entirely. This
corpus hands the join to the model already made. That is a deliberate scope choice and it is the
single biggest thing between this kit and a real reconciliation.
