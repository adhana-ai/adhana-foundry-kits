# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every record from a fixed seed
(`SEED = 20260812`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260812` |
| licence | **MIT** — this repository's own licence, verified against `LICENSE` at the repo root on 2026-08-12 |
| records | 288 in `data/records.csv` |
| labelled pairs | 120 in `data/labelled.jsonl` — 60 same, 60 different |
| formats | csv, jsonl |

## Why invented data, when real customer lists exist

Because the alternative is a licence argument we would lose. Every public dataset of real people is
either scrubbed to the point of removing the mess this kit exists to measure, or it carries terms that
a public MIT repository cannot honour. Generating the corpus removes the question entirely: nobody's
personal data is here, and the file can be regenerated by anyone who clones this.

**The names, addresses and emails are fictional.** `example.com` and `example.net` are the domains
reserved by RFC 2606 for exactly this purpose, so no address here can reach anybody.

## What it cannot tell you

⚠︎ **An invented corpus contains the failure modes we thought to plant and no others.** That is a real
limit and it is on the published report as well as here. A live customer list will contain kinds of
mess this set does not — transliterated names, addresses in formats we did not model, records merged
badly by a previous system. The kit measures how a matcher handles **eight named traps**; it does not
measure how it handles your data.

## The traps, and why each one is in here

Nine categories, counted and asserted by `tools/build_corpus.py::audit` — a census no code checks is a
census that goes wrong, and the sibling text-to-SQL kit already paid for that once with 117 accidental
name collisions under a comment claiming one.

**Pairs that ARE the same person** — a matcher that says "different" fails these:

| trap | what it looks like | n |
|---|---|---|
| `nickname` | Kathryn → Kate, surname intact | 12 |
| `abbreviation` | `88 Ferndale Rd` vs `88 Ferndale Road` | 12 |
| `surname-change` | a married or hyphenated surname, both spellings live | 12 |
| `transposed-dob` | `1990-11-02` vs `1990-02-11` | 7 |
| `email-variant` | the same person's address written two ways | 17 |

**Pairs that are NOT the same person** — a matcher that says "same" destroys data:

| trap | what it looks like | n |
|---|---|---|
| `relative` | one address, shared surname and initial, different date of birth | 12 |
| `twin` | one address, one date of birth, forenames a letter apart | 6 |
| `namesake` | the identical name, nothing else shared | 10 |
| `unrelated` | two records with no relationship, as a control | 32 |

⚑ **The hard negatives are the ones that matter, and the free matcher fails every one of them.**
`evals/baseline.py` measures it: at **every** threshold from 0.50 to 0.95, weighted string similarity
merges the relatives and the twins — because every field it can compare agrees. There is no setting at
which this corpus can be deduplicated safely by string comparison, which is precisely the gap a model
is being asked to close.
