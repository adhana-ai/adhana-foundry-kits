# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every statement from a fixed seed
(`SEED = 20260820`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260820` |
| licence | **MIT** — this repository's own licence |
| statements | 55, in `data/corpus/*.txt` |
| gold | 55 rows in `data/gold.jsonl` |
| account holders / institutions | invented names and invented bank/brokerage names, sampled without any link to a real person or company |

## Why an invented set of statements, when real ones exist

**Because a real bank or brokerage statement cannot be published at all.** It is one of the most
sensitive documents a person holds — an account number, a real balance, a real employer's name, a
real transaction history. There is no public corpus of (statement, underwriter-confirmed asset
figures) pairs, for the same reason no public corpus of tax returns or paystubs exists: the
interesting cases are exactly the ones nobody can publish.

**Nothing in here refers to a real person, employer or financial institution.** Every name, every
institution and every dollar figure is invented; none states a real account.

## The mechanic: one call per statement, ten fields

Each statement gives the model a header (holder, institution, account type, period, beginning and
ending balance) and a list of deposit lines for the period. The model extracts all ten fields,
including which deposit was the period's largest and whether its description names a verifiable
institutional counterparty. See `src/prompt.py`.

## The planted ambiguity: a keyword is not a counterparty

The eval this kit exists to run is whether a model checks for a NAMED, verifiable counterparty or
pattern-matches on a keyword. A deposit described only as "Payroll Deposit" or "Direct Deposit"
with no employer named reads as payroll on a keyword scan and is not actually verifiable against
any specific employer; a deposit posted as "ACH CREDIT ACME LOGISTICS INC" never says the word
"payroll" at all and names a real, checkable employer. `AMBIGUOUS_FRACTION = 0.40` in
`tools/build_corpus.py` controls how often a large deposit is written in one of these confusable
forms.

Gold always records the TRUE documented state, derived from which generator branch produced the
line — never re-derived from the description text a scorer or a model might also read, so the
label cannot inherit whatever mistake a keyword heuristic would make on the same words.

## The unflagged case is the safety-critical one

`large_deposit_flag` in gold is true exactly when the largest deposit is at or above
`LARGE_DEPOSIT_THRESHOLD_USD` (**$1,000 — this kit's own stated policy, not a real loan program's
published guideline; see the README's Cost & effort section**) and its true documented state is
`no`. The eval this kit is built to run cares most about the FALSE NEGATIVE on this flag — a large,
undocumented deposit the model marked `deposit_documented: yes` and so never got routed for
review — because that is the one that actually costs someone a loan file with an unverified deposit
in it. `evals/judge.py` reports it as its own named figure, never folded into a generic accuracy
score.

## What it cannot tell you

⚠︎ **This kit reads one statement at a time and never nets multiple accounts together.** A real
underwriting file usually holds several statements per applicant (checking, savings, sometimes a
brokerage account) and totals "available funds" across all of them. This corpus and this kit's
pipeline compute a per-statement reserve figure only (`ending_balance x a stated vesting
percentage`, see README); summing across an applicant's full asset picture is a step this kit does
not take.

⚠︎ **Program eligibility varies by loan program and this corpus does not model it.** Which asset
types count, at what percentage, and what counts as "large" varies by agency and by investor.
`LARGE_DEPOSIT_THRESHOLD_USD` and the vesting percentages below are one kit's own simplification,
stated plainly so nobody mistakes them for a real program's published guideline.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real
statement carries confusions this one does not attempt — a deposit that is genuinely a gift with a
signed gift letter attached elsewhere in the file, a payroll deposit under a DBA that does not
match the applicant's stated employer, a large deposit that is actually several smaller ones
structured to stay under a reporting threshold. A model that clears this corpus has cleared what
this corpus tests, not every way a real statement can go wrong.
