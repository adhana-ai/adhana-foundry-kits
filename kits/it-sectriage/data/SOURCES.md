# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every case window, alert and gold label
from a fixed seed (`SEED = 20260819`), so the corpus is byte-identical on every rebuild and there
is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260819` |
| licence | **MIT** -- this repository's own licence |
| windows | 33 in `data/windows.jsonl`, each 2-4 alerts |
| alerts | 82 total, across 5 alert types |
| gold | 33 rows in `data/gold.jsonl` -- `alert_facts`, `alert_dispositions`, `case_groups`, `trap` |
| users, hosts, domains, IPs, hashes | all invented; every "external" IP is drawn from the RFC 5737 documentation ranges (`203.0.113.0/24`, `198.51.100.0/24`) which cannot resolve to anyone's real host |

## Why an invented alert stream, when real ones exist

**Because a real one cannot be published at all.** A real SOC's alert queue names real users, real
hosts and real attacker infrastructure -- this repo has never held one and is not able to. There is
no public corpus of paired (alert group, adjudicated disposition, confirmed incident grouping)
records, for the same reason no public corpus of production payment runs or vendor contracts
exists: the interesting cases are exactly the ones nobody can publish.

## The mechanic this corpus tests

Every window is a pre-selected group of 2-4 alerts that a SOC already bundled because they
occurred close in time and/or share an entity (a user or a host). One model call per window has to:

1. classify every alert `true_positive` or `false_positive`,
2. decide which of the true positives are genuinely the SAME incident (`case_groups`), and
3. draft one containment recommendation per case, citing a real indicator.

`case_groups` is **derived, never authored independently**: every alert this file builds is tagged
at construction time with a disposition and a `case_id` (a false positive gets no `case_id`), and
`derive_gold()` in `tools/build_corpus.py` is the one function that turns those per-alert facts
into the `alert_dispositions` dict and the `case_groups` list -- used both at generation time and,
independently, by `--verify` against `data/gold.jsonl` as written to disk.

| pattern | windows | what it is |
|---|---|---|
| `correlated_tp` | 7 | one genuine incident, every alert a true positive, no trap (except the phishing cluster below, which doubles as a false_negative-trap window) |
| `uncorrelated_fp` | 6 | 2-3 false positives with nothing in common -- the correct answer is no case at all |
| `mixed_tp_fp` | 7 | one real, solo incident buried among 1-2 unrelated false positives |
| `multi_incident` | 5 | two genuinely separate real incidents in one window, sharing no entity or indicator |
| `false_correlation_trap` | 8 | the second named trap -- see below |

## The two named traps, planted on purpose, and exactly which windows carry them

### 1. False negative: a true positive worded like a routine question

A real phishing report often reads as a calm "is this legit?" rather than an alarm. **3 of the 9
true-positive `phishing_report` alerts in this corpus (33%) are written in that mundane register**
-- `data/gold.jsonl`'s `trap: "false_negative"` and `trap_alert_ids` name them exactly:

| window | alert | text register |
|---|---|---|
| `cw006` | `ALT-0011` | "asks whether an email about a benefits enrollment deadline is really from HR" |
| `cw014` | `ALT-0030` | "wants to know if it's legitimate before clicking anything" (password reset) |
| `cw015` | `ALT-0032` | "just double-checking" an invoice email with slightly different payment details |

`cw006` is also a `correlated_tp` window -- the mundane report shares its `sender_domain` and
`link_domain` with a second, alarmingly-worded phishing report from the same campaign, so it
doubles as a test of whether a decider can use a loud neighbour's evidence to correctly classify a
quiet one, without being TOLD they are linked in advance.

### 2. False correlation: a coincidental shared indicator, not a shared incident

Two alerts that share an entity, a close timestamp, or one indicator value are not necessarily one
incident -- most often in this corpus, the same building's or VPN concentrator's egress IP,
coincidentally shared by two unrelated users. **8 of the corpus's 26 windows that present a
genuine merge-or-don't decision (any window with 2+ alerts that are not already one single
incident by construction -- i.e. every window except the 7 `correlated_tp` windows) carry this
trap, 31%.** `data/gold.jsonl`'s `trap: "false_correlation"` and `trap_pair` name the exact two
alert ids that must NOT end up in the same case:

| window | trap_pair | shape |
|---|---|---|
| `cw026` | `ALT-0061`, `ALT-0063` | real brute-force + login pair (2 alerts, 1 case) vs. an unrelated benign travelling-user login sharing the same source IP |
| `cw027` | `ALT-0064`, `ALT-0066` | same shape |
| `cw028` | `ALT-0067`, `ALT-0069` | same shape |
| `cw029` | `ALT-0070`, `ALT-0072` | real brute-force alone (1 alert, 1 case) vs. a SEPARATE genuine true-positive login incident, sharing the coincidental IP |
| `cw030` | `ALT-0073`, `ALT-0075` | same shape as `cw026` |
| `cw031` | `ALT-0076`, `ALT-0077` | same shape as `cw026` |
| `cw032` | `ALT-0078`, `ALT-0079` | real brute-force + login pair vs. a separate genuine true-positive incident, sharing the coincidental IP |
| `cw033` | `ALT-0080`, `ALT-0082` | same shape as `cw026` |

6 of the 8 pair the real incident against an unrelated **false positive** (a benign travelling
user, per this kit's own worked example in the spec); 2 of the 8 (`cw029`, `cw032`) pair it against
a **second, separate true positive** instead -- so the trap is tested both against noise and
against a genuinely different real incident, not only the easier of the two shapes.

`evals/scoring.py::score()` takes `fn_trap_alert_ids` and `fc_trap_pairs` as explicit arguments
(both built directly from `data/gold.jsonl`'s `trap`/`trap_alert_ids`/`trap_pair` fields) precisely
so both trap-specific rates can be reported apart from the corpus-wide rate, never inferred by
re-guessing which windows "look like" a trap after the fact.

## The free floor demonstrates both traps concretely

`evals/baseline.py`'s keyword-and-shared-indicator rule is not tuned to lose: it independently
misses **2 of 3** false-negative-trap alerts (the third is rescued by its loud campaign neighbour,
see `cw006` above) and over-merges **8 of 8** false-correlation-trap pairs -- because a rule that
groups first by raw similarity and only then asks whether the group looks bad will, by
construction, drag an unrelated alert into a real incident's case the moment it shares one
indicator value. That is not a strawman weakening; it is what "same IP, must be one incident" looks
like as code, and it is exactly the mistake a rushed read makes.

## What it cannot tell you

⚠︎ **Indicator coverage is assumed complete for every alert in this corpus.** A real alert from a
security tool this deployment has no integration for would carry fewer indicators, or none, and
this kit has no way to notice that an alert's evidence is incomplete rather than merely thin. See
the guardrail note in `README.md`.

⚠︎ **The case-window boundary itself is authored, not computed.** This kit assumes the 2-4 alert
grouping it is handed is already reasonable -- which alerts get bundled together in the first place
is a real, operator-tuned entity/time correlation window upstream of anything here. Too loose over-
merges before a model ever sees the alerts; too tight splits one real incident across two windows
that never get compared. Nothing in this kit measures that upstream choice.

⚠︎ **Every window carries at most one of the two named traps.** A real SOC queue can carry both
kinds of trouble in the same bundle at once; this corpus keeps them apart so each failure mode is
legible on its own.

⚠︎ **The false-correlation trap's "coincidental shared indicator" is always a source IP in this
corpus.** A real deployment sees the same failure shape from a shared device fingerprint, a shared
building's badge-reader-adjacent network segment, or a shared vendor mail relay -- this corpus
tests the mechanism with one concrete instrument of it, not all of them.
