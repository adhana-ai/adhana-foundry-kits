# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every utility billing-account record
from a fixed seed (`SEED = 20260821`), so the corpus is byte-identical on every rebuild and there
is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260821` |
| dataset version | `rate-verify-2026-08-21-55records` |
| licence | **MIT** — this repository's own licence |
| records | 55, in `data/corpus/*.txt`, 24,660 bytes |
| gold | 55 rows in `data/gold.jsonl` |
| accounts / divisions / rate codes | invented identifiers and invented service-division names, with no link to a real utility, tariff filing or customer |

## Why an invented set of billing records, when real ones exist

**Because a real utility billing account record is not something this repo can publish either.**
It names a real customer's account, a real service address and a billing rep's own note about a
specific account. There is no public corpus of (billing record, correctly-applied-rate) pairs, for
the same reason there is no public corpus of bank statements or proof-of-delivery records.

**No real utility, real filed tariff or real published rate schedule is named or reproduced
anywhere in this kit.** "Rate class", "service class", "meter type", "metered usage" and "peak
demand" are ordinary utility-billing vocabulary; every account id, division name, rate code and
billing-rep note here was invented for this corpus.

## The mechanic: one call per record, ten fields

Each record states an account, its service division, its service class, its meter type, the
billing period, the metered usage, the peak demand reading, the rate code actually applied on the
bill, whether the bill has already been sent, and the billing rep's own free-text account note.
The model extracts ten fields — everything except the service division, which no field maps to
and which is therefore never sent — including the one it has to decide: whether the applied rate
code is the one this account actually qualifies for. See `src/prompt.py`.

## The rule, and the priority order a model reading it casually gets wrong

```
correct_code(service_class, meter_type, usage_kwh, demand_kw):
    Residential                                          -> R-1
    interval meter AND usage_kwh >= 15000                -> TOU-8   (checked BEFORE demand)
    demand_kw >= 50                                       -> GS-2
    otherwise                                             -> GS-1
```

Three things about that rule are stated to the model in full, because each is a reading a model
falls into on its own:

| | |
|---|---|
| **service class decides Residential outright** | usage and demand never move a Residential account off R-1, however much it uses |
| **the time-of-use override outranks the demand threshold** | an interval-metered account at or above 15,000 kWh qualifies for TOU-8 **regardless of its demand reading** — checking demand first and stopping there is the wrong order. **15 of these 55 records exercise this override**, and 8 sit exactly on the demand boundary as well, so the sharpest case is measured rather than assumed away |
| **the demand boundary is inclusive** | exactly 50 kW qualifies for GS-2, not GS-1 |

The rule lives in one function — `tools/build_corpus.py::correct_rate_code()` and
`src/extract.py::correct_rate_code()` are the same three-branch logic, used to write gold and to
re-derive it from the model's own reply — and is stated to the model by `src/prompt.py`, so the
kit cannot drift about what "correct" means.

## The planted ambiguity: correctness is structured data, and the note disagrees with it

`N_AMBIGUOUS = 22` puts a billing-rep note from the wrong register on exactly 40% of records:

- a genuinely misrated account carrying a breezy note — "Standard account, nothing unusual to flag
  this cycle." — while the four structured values say otherwise;
- a correctly-rated account carrying a note that reads like a flagged problem — "Escalated last
  cycle for a possible rate misclassification -- pending manager review."

Gold's `rate_correct` is **never** derived from the note. It is the four-value comparison, run
over the same values the record itself states.

`evals/check_labels.py` re-runs that comparison over every gold row before a run is allowed to
spend, and fails if any label disagrees with its own values — and separately asserts that every
note template in `tools/build_corpus.py` classifies to the register it was written as, against the
free floor's own keyword list, before anything may spend. A sibling kit earlier in this series
shipped a keyword that fired on a negation inside a breezy note and mis-registered four records for
days; that check is written into this kit's gate from the start rather than found live.

## The composition is exact, then shuffled — not drawn per record

Several sibling kits in this series draw each record's class from an independent coin, which is
fine at 500 records and is not fine at 55 — a first version of the immediately-preceding kit's
generator asked for 40% ambiguity and delivered 51%. So each class here is a fixed **count**,
shuffled by the seeded RNG. The corpus is still deterministic and still byte-identical on every
run; what changes is that the numbers on the page are the numbers the design asked for.

The mix on this seed:

| | |
|---|---|
| correctly rated | 28 |
| misrated | 27 |
| — service-class swap (a commercial code on Residential, or vice versa) | 6 |
| — demand-boundary swap (GS-1/GS-2 crossed at the 50 kW line) | 9 |
| — the TOU-8 override missed (GS-1/GS-2 applied when TOU-8 was correct) | 8 |
| — TOU-8 wrongly applied (account does not qualify for it) | 4 |
| account note from the contradicting register | 22 (40%) |

| exercising the TOU-8-outranks-demand override | 15 |

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` routes a record for a billing follow-up when the applied rate is wrong
**and** the bill has already been sent to the customer. A misrated account still in draft can
simply be corrected before it goes out; the same mismatch on a bill already sent means the
customer needs a corrected bill or a credit.

⚠︎ **This is the kit's own simplification, not a real utility's billing-adjustment policy.** No
published tariff, regulatory rule or utility's own adjustment procedure was consulted, and none is
reproduced. A real billing desk weighs the dollar size of the correction, how many cycles it has
been wrong, and any regulatory notice requirement; this is two booleans, chosen because it is the
smallest rule that is genuinely useful and readable off one reply.

## What it cannot tell you

⚠︎ **This kit checks and routes only — it never issues a corrected bill, files a tariff exception
or contacts a customer.** `rate_correct` is an extracted field and `needs_review` is a routing
signal; nothing here disposes of anything.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real billing
queue carries confusions this one does not attempt — a mid-cycle rate-class change, a customer on
a special contract rate outside the standard schedule, a meter exchange partway through a billing
period, or a multi-premise account billed under one rate code for several service points. A model
that clears this corpus has cleared what this corpus tests, not every way a rate application can
go wrong.
