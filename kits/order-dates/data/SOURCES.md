# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every scheduling order from a fixed seed
(`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `order-dates-2026-08-22-52orders` |
| licence | **MIT** — this repository's own licence |
| orders | 52, in `data/corpus/*.txt`, 57,002 bytes |
| obligations | 260, across 338 numbered paragraphs |
| gold | 52 rows in `data/gold.jsonl`, one per order, each carrying its own obligations |
| counting rulebook | `data/rulebook.json` — **written for this kit**, see the warning below |
| court / matter / events / items | invented court name, invented matter-number format, invented event vocabulary, invented obligations, with no link to any real court, judge, case, docket, party or jurisdiction |

## ⚠︎ The counting rulebook is illustrative and is NOT an authority

**`data/rulebook.json` (MV-CR-1) was authored for this kit.** It reproduces **no** procedural code,
**no** court rule or local rule, **no** standing order and **no** published court holiday schedule
of any real jurisdiction. Nothing in it was copied from, derived from, or checked against any such
document, because none was consulted.

**Meridian Vale is not a place and the Meridian Vale Civil Court is not a court.** Every court
holiday on the list is invented, name and date, and the set was chosen deliberately NOT to
coincide with any real public holiday — several fall on ordinary mid-week days for no reason other
than that a mid-week closure is the case that actually breaks a business-day count. No judge, no
party, no counsel, no case name and no docket number appears anywhere in this kit; the matter
numbers are of an invented shape (`MVC-27-#####`) and the obligations are generic docketing nouns.

It is a small, deliberately readable construction whose only job is to make the *counting* checkable
end to end: what a business day is, whether the day the clock starts on is counted, whether a period
is in calendar days or business days, and what happens when it lands on a day the court is shut.
Its simplifications are visibly not how a real jurisdiction works — most obviously that one rulebook
governs every basis with no room for a rule that counts backwards from trial, no service-method
extension, no tolling, and no distinction between filing and service.

**The real authority for any deadline is the rules that actually govern the matter, the order as
entered, and the docket.** This kit computes a proposed calendar with its own working shown and
names what it could not date. It never files, serves, dockets or waives anything, and nothing in it
is legal advice. That sentence is on the kit's own UI, above the answer, and not only here.

## Why an invented set of orders, when real ones are public

**Because a real scheduling order is a real case.** It names a court, a judge, parties, counsel and
a docket number, and it is somebody's live matter. Publishing a corpus of them — and, worse,
publishing a *gold calendar* asserting what each deadline really falls on — would be publishing
computed legal deadlines against identifiable litigation, which is exactly the thing this kit is
careful never to do. There is also no public corpus of (order, correct calendar) pairs, for the
same reason there is no public corpus of bank statements: the answer is only correct against the
rules of one court on one day, and nobody publishes the pairs.

Generating it also makes the label mechanical: gold's `due_date` is not somebody's reading, it is
`src/calendar_rules.py::compute()` run over the same structured values the paragraph itself states.

## The mechanic: one call per order, a row per obligation

Each order states a court, a division, a matter number, the date it was entered, a **Recorded
Events** table, and a run of numbered paragraphs. Some of those paragraphs set a deadline and some
do not. The model returns two order-level fields and, for every paragraph that sets one, nine
values — what must be done, how the paragraph fixes its date, the period, the triggering event, the
event's own date, any stated date, the parenthetical a party wrote, and the calendar date it
computes. See `src/prompt.py`.

**The rulebook is sent with every call.** Counting a deadline needs a definition of a business day
and the list of days the court is shut, and a model cannot apply a holiday list it has never been
shown. `src/prompt.py::rulebook_block()` renders `data/rulebook.json` into the prompt rather than
restating it in prose, so the model's instructions and the gold dates cannot drift apart about the
same calendar.

## The five ways an order sets a deadline, and the sixth answer

```
due_date(basis, period, order_date, trigger_event_date, stated_date):
    explicit_date              -> the day the Order names. NEVER moved.
    calendar_days_from_order   -> day zero is the Order date; every day counts; ROLLS forward
    calendar_days_from_event   -> day zero is the event; every day counts; ROLLS forward
    business_days_from_order   -> day zero is the Order date; business days only; never rolls
    business_days_from_event   -> day zero is the event; business days only; never rolls
    ... and if the triggering event has NO recorded date -> there is no date. Not the Order
        date, not zero days, not a guess.
```

Five things about that rule are stated to the model in full, because each is a reading a careless
counter falls into on its own — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **the trigger day is day zero** | the day the Order was entered, or the day the event happened, is not counted; counting starts the next day. Inclusive counting is off by one on every period | **198 obligations** count something |
| **business days are not calendar days** | a 10-business-day period is fourteen calendar days at best and more across a court holiday | **72 obligations** |
| **a calendar period rolls; a stated date does not** | a period ending on a weekend or holiday moves forward — sometimes two days, when the neighbouring Monday or Friday is itself a holiday. A date the Order writes out does not move, weekend or not | **46 roll (4 by more than one day); 18 stated dates fall on a non-business day and stay there** |
| **an undated trigger has no date** | the Recorded Events table says "not recorded", so nothing on the face of the Order dates the obligation | **24 obligations** |
| **the parenthetical is a field, not the answer** | a party's own arithmetic, copied as a field and never used | **96 carry one; 40 of those are wrong** |

The rule lives in one function — `src/calendar_rules.py::compute()` — used to write gold, stated to
the model by `src/prompt.py`, and re-run over the model's own reply by `evals/judge.py`. Three
readers, one definition, so the corpus, the prompt and the diagnostic cannot drift about what a
deadline means.

## The planted ambiguity: somebody has already written a date next to the obligation

96 of the 260 obligations carry a parenthetical such as `(counsel's calendar: 19 March 2027)`.
**40 of them are wrong**, in two different ways, and the split is the point:

- **28 are the desk-calendar answer.** They are, exactly, what `evals/baseline.py`'s free floor
  computes — somebody counted forward on a wall calendar, treating business days as calendar days
  and never moving a date off a weekend. `tools/build_corpus.py` **imports that function** rather
  than re-implementing it, so the decoy cannot quietly stop being the mistake it is documented as.
- **12 are an ordinary diary slip** on an obligation whose arithmetic was not even hard — a month
  out, or four days out, on a paragraph a wall calendar would have got right. Those are the ones
  that punish copying rather than counting.

The remaining 56 agree with the rulebook, because most parties get most dates right and a decoy
that is wrong every time is a decoy nobody would ever be fooled by. Gold's `due_date` is **never**
the parenthetical.

## The second decoy: a paragraph that is deadline-shaped and sets nothing

78 of the 338 numbered paragraphs set no deadline at all, and **30 of those are deadline-shaped**:
they name an item, a number and a unit and then strike, withdraw or disapply the requirement —

> *"The requirement that the pretrial statement be served within 14 business days after the case
> management conference is WITHDRAWN and sets no date here."*

Anything that pattern-matches "within N days" into a docket entry produces an obligation the Order
does not impose. On a docketing queue that is a diary entry nobody owes and somebody has to clear,
so it is counted and named on its own as `invented_obligations` rather than averaged into an
accuracy figure. The other 48 mention a date, a page limit or a duty and are ordinary noise.

## The composition is exact, then shuffled — not drawn per paragraph

Each of the nine buckets is a fixed **count**, shuffled by the seeded RNG, and every constructor is
asserted against the rulebook at build time — a constructor that quietly stops producing its own
bucket is exactly the defect an exact composition exists to prevent. So are the obligations per
order (4, 5 or 6, dealt) and the non-deadline paragraphs per order (1 or 2, dealt), so no order has
a predictable shape.

| | |
|---|---|
| `explicit_plain` — a stated date on a business day | 44 |
| `explicit_nonbusiness` — a stated date on a weekend or court holiday, which does **not** move | 18 |
| `cal_order_plain` — calendar days from the Order, landing clean | 38 |
| `cal_order_roll` — calendar days from the Order, rolling forward | 26 |
| `cal_event_plain` — calendar days from a recorded event, landing clean | 30 |
| `cal_event_roll` — calendar days from a recorded event, rolling forward | 20 |
| `bus_order` — business days from the Order | 32 |
| `bus_event` — business days from a recorded event | 28 |
| `undatable` — the triggering event has no recorded date | 24 |
| paragraphs that set no deadline | 78 (of which 30 are deadline-shaped) |
| obligations carrying a party's own calculated date | 96 (40 wrong) |

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises `undatable` when the period runs from a triggering event and the
Order's own Recorded Events table gives that event no date. Nothing on the face of the Order dates
the obligation, so it cannot go on a calendar — it goes on a list for somebody to find out when the
event happened.

⚠︎ **This is the kit's own simplification, not a docketing desk's real policy.** It reads two of
the row's own values and nothing else. A real desk also knows what the file says, what the parties
have agreed, what the clerk's record shows and which of those outranks the others; none of that is
here.

## What it cannot tell you

⚠︎ **This kit computes and proposes only — it never files, serves, dockets, waives or extends
anything, and nothing in it is legal advice.** `due_date` is arithmetic with its working attached;
`undatable` is a routing signal. Nothing here disposes of anything.

⚠︎ **A run that scores perfectly has agreed with `data/rulebook.json`, which is a much smaller
claim than being right about a real order.** The graders measure whether the run applied the shipped
rulebook. They cannot measure whether the rulebook is correct, because the rulebook is this kit's
own construction and no lawyer, clerk or court has looked at it.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real
docketing queue carries confusions this one does not attempt — a deadline counted BACKWARDS from a
trial date that later moves, an extension of time granted by a later order, a period tolled while a
motion is pending, a service-method extension, a difference between filing and service, a
handwritten interlineation, an order that sets a deadline by reference to a rule number rather than
a period, and a scanned or photographed order with no text layer at all. A model that clears this
corpus has cleared what this corpus tests, not every way a docket calculation can go wrong.
