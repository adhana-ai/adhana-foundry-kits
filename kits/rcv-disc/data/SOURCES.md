# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every case from a fixed seed
(`SEED = 20260819`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260819` |
| licence | **MIT** -- this repository's own licence |
| cases | 36 in `data/cases.jsonl` |
| lines | 110 across the 36 cases (avg 3.1/case) |
| gold | 36 rows in `data/gold.jsonl` -- a liable-party call, a discrepant SKU and a cited quantity pair for every case |
| SKUs, PO numbers, case IDs, carrier names | all invented; no real vendor, carrier or company appears anywhere in this corpus |

## Why an invented set of cases, when real ones exist

**Because a real one cannot be published at all.** A real receiving discrepancy names a real
vendor, a real carrier and a real chargeback dollar figure -- this repo has never held one and is
not able to. There is no public corpus of paired (BOL, receiving scan, carrier exception,
adjudicated liable party) records, for the same reason no public corpus of supplier agreements or
production alerts exists (see `data-reconcile`'s own `SOURCES.md` for that argument in full): the
interesting cases are exactly the ones nobody can publish.

## The mechanic: one call per case, three documents, four liable-party values

Every case carries 2-4 SKU lines (most cases: 3), each with a `po_qty`, `bol_qty` and
`received_qty` -- all three always present -- plus one `carrier_exception` field for the whole
case: either absent, or a short note naming exactly one SKU. Exactly one line per case is
genuinely discrepant; the rest are clean (all three quantities equal) filler, so the model has to
find the right line among several rather than notice "something is off."

| liable_party | means | of 36 |
|---|---|---|
| `vendor` | BOL states less than the PO ordered; receiving matches the BOL. The carrier delivered everything it was given. | 8 |
| `carrier` | BOL states the full PO qty; receiving recorded less; the carrier's own exception note names THIS SKU. | 8 |
| `internal` | Same shortfall shape as `carrier`, but nothing on file corroborates it for this SKU -- no exception, or one naming a different SKU. | 14 |
| `insufficient_evidence` | BOL and receiving agree with each other but not the PO (an apparent over-shipment), or more than one quantity disagrees at once. No clean documentary basis for a call. | 6 |

## The trap, planted on purpose

**6 of the 14 `internal` cases (~43%, the same order of magnitude as fin-invval's 45% ambiguous-
phrasing rate and fin-payrun's ~43% trap rate) carry a carrier exception note that is real, on
file, and names a DIFFERENT SKU than the case's own discrepant line.** The other 8 `internal`
cases carry no exception note at all, so a checker also has to get the plain, uncorroborated case
right, not just the one with a decoy on file.

**This is a data-shape trap, not adversarial text.** The exception note is never fabricated to
deceive -- it is a genuine note about a genuine, different line's transit problem, exactly the kind
of thing that legitimately sits on file next to an unrelated discrepancy. The only way to get the
case right is to check WHICH SKU the note names, not just whether one exists.
`classify_case()` in `tools/build_corpus.py` is the single implementation of the four-way rule; it
labels gold at generation time and, independently, via `--verify`, re-checks every case against
the record actually written to disk. `evals/scoring.py`'s `wrong_sku_exception_misread` is the
metric that measures a reader falling into it.

## What it cannot tell you

⚠︎ **This corpus assumes every case's documentary evidence is complete.** A real deployment where
a BOL or a receiving scan simply never got captured looks, to this kit, identical to a document
that never existed -- this corpus does not attempt to model a genuinely missing document, only a
case where the three that exist do not resolve cleanly. A missing document in production weakens
the liability call in a way this corpus's `insufficient_evidence` design does not cover.

⚠︎ **One fixed liability-attribution rule, not a per-relationship agreement.** A real vendor/
carrier relationship's actual agreement can vary the attribution logic case by case (who bears
transit risk, at what point title transfers); this corpus applies the single stated four-way rule
above to every case, the same way `data-reconcile` documents its own per-supplier limitation.

⚠︎ **Every case carries at most one discrepant line.** A real receiving dock can find more than
one line short on the same shipment at once; this corpus plants exactly one per case to keep the
failure mode legible.

⚠︎ **The trap denominator is small.** 6 trap cases is what a corpus of this scale supports
honestly; a wider real deployment would want a larger sample before trusting the
`wrong_sku_exception_misread` rate as a stable number. It is reported as a raw count alongside the
rate for exactly this reason -- see `evals/scoring.py`.
