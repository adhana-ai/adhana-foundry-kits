# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every attestation register from a fixed
seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `attestation-watch-2026-08-22-50registers` |
| licence | **MIT** — this repository's own licence |
| registers | 50, in `data/corpus/*.txt`, 84,238 bytes |
| attester rows | 280 people across those 50 registers, 4 to 7 per register |
| gold | 50 rows in `data/gold.jsonl` — one per register, each carrying its whole roster |
| cycle rulebook | `data/rulebook.json` — **written for this kit**, see the warning below |
| engagements / people / relationships / notes | invented references, invented roles, invented relationship descriptions, invented administrator notes, with no link to any real firm, client, engagement or person |

## ⚠︎ The rulebook is illustrative and is NOT an authority

**`data/rulebook.json` was authored for this kit.** It reproduces **no** real professional standard,
**no** standard-setter's rule, **no** regulator's requirement and **no** firm's own independence
policy. Nothing in it was copied from, derived from, or checked against any such document, because
none was consulted. **No real firm, standard-setter, regulator, standard number, client or person is
named anywhere in this kit.**

It is a small, deliberately readable construction whose only job is to make the *decision shape*
measurable: an applicability gate, a determinability gate, a cycle length that produces a due date
by arithmetic, a grace window, a coverage test, and two ways a register can contradict itself.
Several of its simplifications are visibly not how a real engagement works, and are named as such in
the file itself — most obviously that one cycle length applies to a role regardless of the client,
the assignment or anything the person actually does.

**The real authority for an independence question is the standard your firm is actually bound by,
the engagement's own terms, and a person qualified to read both.** This kit proposes a status with
its reasoning and names what it could not determine. It never authorises, writes, dispatches,
releases or clears anything. That sentence is on the kit's own UI, above the answer, and not only
here.

## ⚠︎ And this kit watches nothing

"Monitoring" here does not mean a daemon, a poller, a stream or a dashboard. **A monitoring
SNAPSHOT is the document.** Each file is one engagement's register as it stood at one moment;
the kit reads it, proposes a worklist, and stops. There is no schedule, no subscription, no queue
and no state anywhere in the repository. It does not poll, subscribe, alert, escalate, chase, file,
sign a register off or clear anybody, and nothing in it runs unattended.

## Why an invented set of registers, when real ones exist

**Because a real independence register is not something this repo can publish either.** It names
real people on a real engagement, their real financial and family relationships, a real client, and
a named administrator's own remark. There is no public corpus of (attestation register, correct
worklist) pairs, for the same reason there is no public corpus of bank statements or HR files.

Generating it also makes the label mechanical: gold's `status` and gold's `due_on` are both
`src/rulebook.py` run over the same values the register itself states, never somebody's reading of
the administrator's note.

## The mechanic: one call per register, four register fields and eleven per person

Each register states an engagement reference, the date it was assembled, the rulebook it is kept
under, a roster of people with their roles and the date each person's cycle opened, every return
filed with its date, the period it covers and what it declared, what the register records about
those declared relationships, any roster changes, and the administrator's own free-text note. The
model returns four register-level fields and one object per person on the roster — everything except
the `Prepared By` section, which no field maps to and which is therefore never sent. See
`src/prompt.py`.

**The rulebook is sent with every call.** The cycle lengths and the grace window are a lookup, and a
model cannot look up a table it has never been shown. `src/prompt.py::rulebook_block()` renders
`data/rulebook.json` into the prompt rather than restating it in prose, so the model's instructions
and the gold labels cannot drift apart about the same arithmetic. Measured on the worked example:
566 of 3,067 input tokens (18%) are the rulebook, and **1,169 (38%) are the field schema** — eleven
per-person fields each need a hint long enough to be unambiguous, and on this kit the schema is the
expensive part, not the table.

## The rule, and the order a reader gets wrong

```
status(person, register):
    role vacated / joined mid-cycle / a role with no requirement  -> not_required
    no cycle date, or a return whose covered period is not stated -> not_determinable
    no return on file at all                                      -> missing
    two returns that disagree, or a relationship the register
      records as disposed BEFORE the return that declares it      -> contradicted
    filed later than due + grace, or covering a period that ends
      before the due date                                         -> stale
    otherwise                                                     -> satisfied
```

`not_required` is first, and `not_determinable` is second, and both positions are the point.

Five things about that rule are stated to the model in full, because each is a reading a careless
monitor falls into on its own — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **the applicability gate comes first** | a vacated role, a mid-cycle joiner and a role the rulebook puts no requirement on all owe nothing, and all three usually have no return on file. Equating "no form" with "gap" chases every one of them | **40 rows**, of 280 |
| **the same roster line means two different things** | `cycle opened -- not recorded on this register` appears both on somebody who joined last week and on a record nobody can read. Only the **Roster Changes** section separates them, and it is a different section | **14 joiners, 8 unreadable records** |
| **the order of two dates decides a contradiction** | disposed BEFORE the return that declares it, the register contradicts itself; disposed AFTER, the return was correct on the day it was filed, which is the only day a return can be correct about | **16 before, 12 after** |
| **inside the grace window is in time** | a return filed after the due date looks late and is not. Comparing two dates and stopping there is the second-largest source of false alarms here | **22 rows** |
| **the due date is derived, never read** | no register states one. It is the cycle-opened date plus the rulebook's cycle length for the role, and for a role with no cycle length the correct answer is *no date at all* rather than a guess | **12 rows** where the correct due date is null |

The rule lives in one function — `src/rulebook.py::decide()` — used to write gold, stated to the
model by `src/prompt.py`, and re-run over the model's own reply by `evals/judge.py`. Three readers,
one definition, so the corpus, the prompt and the scorer cannot drift about what a status means.

## The planted ambiguity: the administrator's note disagrees with the register

Exactly **20 of the 50 registers (40%)** carry a note from the wrong register:

- a register with people to chase, carrying a settled note — *"Standard rollover, nothing unusual
  about this engagement's declarations at all."*;
- a register with nothing outstanding, carrying an alarmed one — *"Flagged this register for a
  second pass before sign-off; the paperwork looks uneven to me."*

Gold's `status` is **never** derived from the note. It is the rulebook run over the same values the
register itself states.

`evals/check_labels.py` re-runs the rule over every gold row before a run is allowed to spend, and
fails if any label disagrees with its own values or if any derived date disagrees with the
arithmetic.

## The composition is exact, then shuffled — not drawn per row

Each of the thirteen buckets is a fixed **count** across the whole corpus, shuffled by the seeded
RNG and dealt into registers whose sizes are themselves an exact multiset. Every constructor is
asserted against the rule at build time — a constructor that quietly stops producing its own bucket
is exactly the defect an exact composition exists to prevent.

## The routing flag is a business condition, not a check on the model

`src/extract.py::compute()` raises `needs_owner_review` when the register carries at least one
`contradicted` person **or** at least one `not_determinable` one. A missing or stale attestation is
cleared by asking somebody for a form; a contradiction and an unreadable record are not, and routing
them to the same queue as a chase is how they get buried under it.

⚠︎ **This is the kit's own simplification, not anybody's escalation policy.** No firm's procedure,
professional standard or regulatory rule was consulted, and none is reproduced. A real practice
weighs who the person is, what the engagement is, how close sign-off is, and who already knows.

## What it cannot tell you

⚠︎ **This kit reads and proposes only — it never chases, files, signs a register off or clears
anybody.** `status` is computed and returned; `needs_owner_review` is a routing signal; nothing here
disposes of anything.

⚠︎ **A run that scores perfectly has agreed with `data/rulebook.json`, which is a much smaller claim
than being right about a real engagement.** The graders measure whether the run applied the shipped
rulebook. They cannot measure whether the rulebook is correct, because the rulebook is this kit's
own construction.

⚠︎ **EVERY REQUIRED ATTESTER'S DUE DATE HAS PASSED AT THE REGISTER'S AS-AT DATE, BY CONSTRUCTION.**
A "not due yet" case is a seventh status this kit does not carry, so the corpus does not contain one
and `evals/check_labels.py` asserts that it does not. On a real register that case is common, and
this kit would call every one of those people `missing`.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real
attestation register carries confusions this one does not attempt — a person on two engagements with
two cycles, a return filed against the wrong engagement, a relationship declared by a family member
rather than the attester, a role that changed mid-cycle rather than being vacated, a register merged
from two systems with two spellings of one person, and a rulebook that changed part-way through a
cycle. A model that clears this corpus has cleared what this corpus tests, not every way a register
can go wrong.
