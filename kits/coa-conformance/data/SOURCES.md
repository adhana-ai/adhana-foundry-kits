# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every certificate of analysis from a
fixed seed (`SEED = 20260821`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260821` |
| dataset version | `coa-conformance-2026-08-21-55records` |
| licence | **MIT** — this repository's own licence |
| records | 55, in `data/corpus/*.txt`, 27,669 bytes |
| gold | 55 rows in `data/gold.jsonl` |
| products / batches / analysts | invented names and invented batch numbers, with no link to a real manufacturer, brand or lot |

## Why an invented set of certificates, when real ones exist

**Because a real certificate of analysis is not something this repo can publish either.** It names
a real manufacturer, a real customer's lot and a real release decision — and the disposition note
on it is a named analyst's own words about a batch that shipped. There is no public corpus of
(certificate, conformance outcome) pairs, for the same reason no public corpus of bank statements
or pay stubs exists.

**No real specification, standard, monograph or company is named or reproduced anywhere in this
kit.** "Certificate of analysis", "specification limits" and "release testing" are ordinary
quality-control vocabulary; every limit, product and note here was invented for this corpus.

## The mechanic: one call per certificate, ten fields

Each record states a batch, a product, one test parameter, the measured result and its unit, the
two specification limits — either of which may be absent on a one-sided specification — the test
date, and the analyst's own free-text disposition note. The model extracts all ten fields,
including the one it has to decide: whether the measured value falls inside the stated limits.
See `src/prompt.py`.

## The planted ambiguity: conformance is arithmetic, and the prose disagrees with it

The eval this kit exists to run is whether a model **does the comparison** or **reads the analyst's
tone**. `AMBIGUOUS_FRACTION = 0.40` puts a note from the wrong register on a deliberate share of
records; the achieved figure on this seed is **24 of 55 (44%)**:

- a batch a hair **outside** its limits carrying a reassuring note — "Within normal range for this
  product line. Released to finished-goods inventory." — while the number says otherwise;
- a batch sitting cleanly **inside** its limits carrying a hedging one — "Borderline in my
  judgement. Recommend a re-test on a second sample before release."

Gold's `conforms_to_spec` is **never** derived from the note. It is the arithmetic, run over the
same measured value and limits the document itself states, with the same boundary-inclusive rule
the kit publishes:

```
conforming  <=>  (lower is None or measured >= lower) and (upper is None or measured <= upper)
```

`evals/check_labels.py` re-runs that comparison over every gold row before a run is allowed to
spend, and fails if any label disagrees with its own numbers. `tools/build_corpus.py::_verify()`
separately confirms every gold value is stated verbatim in the document it labels, and that every
`test_date` is a real calendar date.

**Values are never generated exactly on a limit.** The published rule is boundary-inclusive, and a
corpus that tested the boundary would be testing the convention rather than the arithmetic. The
generator redraws until the value survives rounding on the side it was meant to land on — a value
drawn 0.005 outside an upper limit and printed to two decimals lands *on* the limit in the
document, and the label has to follow what the document says, not what the draw intended.

The mix on this seed: **29 conforming, 26 out of specification, 31 records with a one-sided
specification** (a null limit on one side, which a model has to return as `null` rather than
inventing a bound).

## The guardrail is a self-consistency check, not a business rule

`src/extract.py::compute()` re-runs the same comparison over the numbers **the model itself
extracted**, and raises `needs_review` when that recomputation disagrees with the model's own
`conforms_to_spec`. It uses no gold and no second call, so it computes on a certificate nobody has
labelled — which is the point. On this corpus it caught **24 of 24** of the free tone floor's
verdict errors (`evals/baseline.py`, `results/eval-b000-rules.json`) and fired **zero** times on
either model tier, both of which answered consistently on all 55 records.

## What it cannot tell you

⚠︎ **This kit checks and flags only — it never releases or rejects a batch.** `conforms_to_spec`
is an extracted field and `needs_review` is a routing signal; nothing here dispositions anything.
A real release decision belongs to a qualified person against a real, approved specification.

⚠︎ **The specification limits are invented.** Every parameter, unit and limit in `PARAMETERS`
(`tools/build_corpus.py`) was made up to give the arithmetic something to bite on. None is taken
from, or intended to resemble, any real published standard or any real product's approved
specification.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real quality
queue carries confusions this one does not attempt — a result reported in a different unit from the
specification, a limit expressed as a percentage of a target rather than an absolute, a specification
that changed between the test date and the review, a re-test result that supersedes the first, or a
parameter where the analytical method's own uncertainty is wider than the gap to the limit. A model
that clears this corpus has cleared what this corpus tests, not every way a conformance call can go
wrong.
