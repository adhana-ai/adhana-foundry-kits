# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every pay stub from a fixed seed
(`SEED = 20260821`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260821` |
| licence | **MIT** — this repository's own licence |
| stubs | 55, in `data/corpus/*.txt` |
| gold | 55 rows in `data/gold.jsonl` |
| employees / employers | invented names and invented company names, sampled without any link to a real person or company |

## Why an invented set of pay stubs, when real ones exist

**Because a real pay stub cannot be published at all.** It is one of the most sensitive documents
a person holds — a real name, a real employer, a real salary. There is no public corpus of
(pay stub, underwriter-confirmed qualifying income) pairs, for the same reason no public corpus of
tax returns or bank statements exists: the interesting cases are exactly the ones nobody can
publish.

**Nothing in here refers to a real person or employer.** Every name, every employer and every
dollar figure is invented; none states a real income.

## The mechanic: one call per stub, ten fields

Each stub gives the model an employee/employer header, a pay frequency, a year-to-date earnings
summary (base, overtime with a stated periods-paid/periods-total count, and bonus), and a free-text
Bonus History note. The model extracts all ten fields, including whether the bonus history reads
as genuinely recurring. See `src/prompt.py`.

## The planted ambiguity: a label is not a history

The eval this kit exists to run is whether a model checks for an ACTUAL STATED PAYMENT HISTORY or
pattern-matches on a word like "annual". A bonus note that says "Annual performance bonus" with no
payment history stated reads as recurring on a keyword scan and is not documented as continuing; a
note that never says "annual" but states "Bonus paid in both the 2024 and 2025 performance cycles"
IS documented as continuing. `AMBIGUOUS_FRACTION = 0.40` in `tools/build_corpus.py` controls how
often a bonus note is written in one of these confusable forms.

Gold always records the TRUE recurring state, derived from which generator branch produced the
note — never re-derived from the words a scorer or a model might also read.

## The excluded-but-material case is the safety-critical one

The kit's own pure-code computation (`src/extract.py::compute`) excludes overtime from qualifying
income when it was paid in fewer than 75% of this year's pay periods (`OT_CONTINUANCE_THRESHOLD`
— **this kit's own stated policy, not a real loan program's published guideline**; see the
README's Cost & effort section), and excludes bonus income entirely when `bonus_recurring` is
`no`. `needs_review` is true whenever a bonus of $1,000 or more (`LARGE_BONUS_THRESHOLD_USD`) was
excluded — the eval this kit is built to run cares most about whether that flag fires correctly,
because a large excluded bonus is exactly the figure an underwriter would want to double-check
against a separate two-year history document this stub alone cannot prove. `evals/judge.py`
reports it as its own named figure, never folded into a generic accuracy score.

## What it cannot tell you

⚠︎ **This kit reads one stub at a time and never cross-references a separate W-2, tax return or
employer letter.** A real underwriting file often corroborates a stub's bonus/overtime history
against a second document; this kit's continuance determination comes from the stub's own Bonus
History note alone.

⚠︎ **Program eligibility varies by loan program and this corpus does not model it.** Which income
types count, at what continuance threshold, and how many years of history is required varies by
agency and by investor. `OT_CONTINUANCE_THRESHOLD` and `LARGE_BONUS_THRESHOLD_USD` are one kit's
own simplification, stated plainly so nobody mistakes them for a real program's published
guideline.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real stub
carries confusions this one does not attempt — a bonus that changed employer name mid-year after
an acquisition, overtime paid under a title that does not match the base-pay title, a pay stub
whose YTD figures were corrected mid-year by a payroll system migration. A model that clears this
corpus has cleared what this corpus tests, not every way a real pay stub can go wrong.
