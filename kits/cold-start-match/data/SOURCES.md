# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every history item, every new-item
setup request and every gold label from a fixed seed (`SEED = 20260818`), so the corpus is
byte-identical on every rebuild and there is no third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260818` |
| licence | **MIT** — this repository's own licence |
| history items | 120, in `data/history.jsonl` — 24 per category across 5 categories |
| requests | 15 in `data/requests.jsonl` — 3 per category |
| gold | 360 pairwise rows in `data/gold.jsonl` — `like_item` / `not_like_item` for every (request, blocked candidate) pair |
| formats | jsonl (history, requests, gold) |

## Why an invented item catalog, when real ones exist

**Because a real one cannot be published at all.** A real item's vendor spec, its merchant brief
and its measured early sell-through is exactly the kind of commercial detail a retailer will not
let leave the building. There is no public corpus of paired (new-item setup request, prior
comparable items, adjudicated like/not-like, measured early sales) tuples, for the same reason no
public corpus of production alerts or signed supplier agreements exists.

**Nothing in here refers to a real retailer, brand or product.** Categories, materials and
sell-through figures are invented.

## The job is generic; the flavour is not

This kit's actual job — match a new item with no sales history against prior comparable items on
a stated set of attributes, and draft a starting forecast from the ones that qualify — applies to
anything that needs a precedent to lean on when there is no history of its own: a new SKU against
comparable prior SKUs, a new hire's compensation band against comparable prior hires, a new
market's launch plan against comparable prior launches. This corpus happens to flavour the "new
item" as a retail SKU going through cold-start forecast setup and the attribute set as material /
price tier / channel / season, because that is one concrete, checkable instance of the job, not
because the job is about retail. Point `tools/build_corpus.py` at your own attribute set and the
pipeline — `src/block.py`, `src/prompt.py`, `src/forecast.py` — does not change.

## The LIKE_ITEM rule, planted and counted

A candidate history item is a true like item for a request only if **all four** hold: identical
material, identical-or-adjacent price tier (on the fixed order `value, core, premium, luxury`),
identical channel OR both in the online-only family `{ecommerce_only, marketplace}`, and identical
season. `tools/build_corpus.py::is_like_item()` is that rule in code; it is also `src/prompt.py`'s
`RULES` text verbatim in prose, so the two cannot silently drift apart.

Every request gets **3 deliberately planted like items** (one exact match, one exercising the
price-tier allowance, one exercising the channel-family allowance) and **4 deliberately planted
near-misses** (each violating exactly one of the four rules), plus 3 unshaped filler items per
category. `is_like_item()` is then applied uniformly to the whole category pool — a filler item
that happens to satisfy the rule by coincidence is labelled `like_item` too; nothing is
hand-labelled after the fact. Of the 360 pairwise rows this produces, 45 (12.5%) are `like_item`.

## What the exact-match floor cannot tell you

⚠︎ **THE FREE FLOOR (`evals/baseline.py`) IS A REAL BASELINE, NOT A STRAWMAN, AND IT REUSES THE
SAME BLOCKING CODE THE REAL PIPELINE RUNS** (`src/block.py`), so the two are compared on identical
candidate sets — the gap measured between them is entirely in which pairs get counted as like
items, never in who saw a smaller haystack.

⚠︎ **BY CONSTRUCTION, THE FLOOR CAN NEVER FALSE-MERGE ON THIS CORPUS.** It only counts a
candidate as a like item when all four fields are literally identical (score 1.0) — and every
literally-identical pair also satisfies the true rule (identity is a special case of "identical or
adjacent"), so its errors are entirely on the recall side: it misses every candidate that needs one
of the two stated tolerances.

## What was measured, and its limits

Every request in this corpus carries at least 3 deliberately planted like items, so recall is
never measured against a request with zero true comparables in history — a real cold-start
program's precedent base may be sparser, or richer, than what was planted here. See
`Data.bring_your_own_boundary` on the published report for the precise wording of that limit.
