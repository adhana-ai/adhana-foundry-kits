# commission-audit — check a channel's commission claim against the property's own folio

**UC043.** Point it at one line of a booking channel's commission invoice, joined to the property's
own folio record for the booking it names, get a field table back — plus a routing decision taken
afterwards in pure code, from two of the extracted values: is the commission claimed what is
actually owed, and if it is not, has the property already paid the invoice? Nothing here short-pays
an invoice, raises a dispute or contacts a channel; the flag is a routing signal.

MIT. Python standard library plus a minimal JS UI. One model, one key, run once per model.

```bash
python -m evals.check_labels                          # free — validates the gold set
python -m evals.run --run-id b000-rules --baseline    # free — the reviewer-note floor
python -m evals.run --run-id t000-stub --stub         # free — proves the wiring end to end
# provider/key: configure ONCE at the repo root -- ../../.env -- not per kit
python -m evals.run --run-id r001-<model>             # THIS SPENDS MONEY: one call per claim line
python -m src.app                                      # the local UI on 127.0.0.1:8797
```

**You do not need a key to see this kit work, and it will never ask you for one.** The corpus and
every recorded run ship in the repository, so `python -m src.app` renders and stays browsable
offline — with no key it returns a plain sentence saying nothing was called, rather than an error.
`check_labels`, the `--baseline` floor and the `--stub` run all reproduce their published numbers
with no network access at all. A key is needed only to extract a new case or to re-run the eval
against your own numbers.

## The corpus is invented, and it names nobody

Every record is generated by `tools/build_corpus.py` from a fixed seed (`20260822`), byte-identical
on every rebuild. **No real booking channel, OTA, hotel brand, management company, guest or
reservation appears anywhere in this kit** — not in the corpus, not in the field schema, not in the
prompt, not on a published figure. The channel is never named at all: `booking_source` is an enum
whose "came through the channel that issued this invoice" value is the literal token `channel`. A
brand name in a corpus about disputed money is a claim about a real company's invoicing, and this
repository does not make one.

There is no guest in the corpus either. A real folio names one, with an address and a card; none of
that is needed to decide whether a commission is owed, so none of it is here.

⚠︎ **A near-miss is a brand name.** A first version of the property list carried *"Fairmount
Lodge"*, which is one letter from a real global hotel brand, and *"a reader will see it is
invented"* is not a test anybody applies to a name they half-recognise. It was renamed before the
corpus shipped, along with one other name close to a real management company. The property is the
one section no field maps to and which therefore never reaches a model — which is exactly why it is
easy to be careless with it, and exactly no excuse. See `data/SOURCES.md`.

## Whether a commission is owed is a computation. The reviewer's note is not evidence about it.

A claim line and a folio put a booking source, a folio status, several money figures and the
property reviewer's own account of the line on the same page. Only the structured values decide
anything:

```
owed(source, already, status, room_revenue, refunded, penalty, rate):
    source is not 'channel'            -> 0.00        (checked FIRST, before any arithmetic)
    already commissioned               -> 0.00        (checked SECOND)
    status is stayed or rebooked       -> base = room_revenue - refunded
    status is cancelled or no_show     -> base = penalty charged
    non-room charges                   -> NEVER in the base, in any branch
    base <= 0                          -> 0.00
    otherwise                          -> round(base * rate / 100, 2)
```

Five things about that rule are stated to the model in full, because each is a reading a model — or
a person under time pressure — falls into on its own:

| | |
|---|---|
| **the booking source outranks everything** | a stay the folio shows arrived direct, through a corporate GDS or as a walk-in owes this channel nothing, however real the stay and however tidy the arithmetic. **5 of these 55 records are exactly that**, and every one carries a perfectly correct multiplication |
| **nothing is owed twice** | **4 records** were already commissioned on a previous invoice, with every other value on the line right. Both of these branches settle the answer *before* any multiplication happens, which is the whole shape of this rule |
| **taxes and fees are never in the base** | **6 records** compute commission on the folio total. The tax line sits directly beside room revenue, which is what makes it the commonest bad claim there is |
| **a cancellation is not automatically zero** | **9 records** are a cancellation or no-show with a penalty actually charged, and commission IS owed — on the penalty, never on the room revenue nobody earned. **All 9 are valid claims**, so a reader who stops at "the guest did not stay" gets every one of them backwards. The 4 records cancelled with *no* penalty charged are the mirror case and are all invalid |
| **a rebooked reservation is a stay** | **5 records** moved to a new confirmation number and the guest stayed. They are commissionable on room revenue exactly as a plain stay is |

**9 records carry a partial refund**, split between claims that correctly used the net room revenue
and claims that used the gross.

The rule lives in one function, `owed_commission()`, and is used in three places — the corpus
generator that wrote gold, the prompt that asks the model, and the scorer that re-derives gold's own
truth at score time — so the kit cannot drift about what "owed" means.

## The guardrail is a business condition, and it needs labels — which is the honest half

`src/extract.py::compute()` routes a claim when the commission is not owed as claimed **and** the
invoice has already been paid. It answers the question a hotel finance desk actually has:

> **Is this the line somebody has to chase today?**

A bad line on an unpaid invoice can simply be short-paid before settlement — no money has left the
property and there is nothing to recover. The same line on an invoice already paid means the
property is out of pocket and has to raise a recovery claim against the channel, inside whatever
dispute window that agreement allows.

⚠︎ **This is the kit's own simplification, not a real property's dispute policy.** No booking
channel's published dispute procedure, no signed distribution agreement and no property's own
recovery threshold was consulted, and none is reproduced. A real desk weighs the dollar size of the
variance, whether the dispute window is still open, and the cost of raising a claim at all — and
**this corpus carries no field for what a variance is worth**, which is the first thing a real desk
would sort on. Two booleans is the smallest rule that is genuinely useful and readable off a single
reply, and it should be the first thing a forker replaces.

Because it is a business condition, **it can only be scored where somebody wrote down the right
answer**. The kit is explicit about that, and it reports a no-gold *consistency diagnostic* beside
it (does the reply's own verdict survive the computation re-run over the reply's own numbers?)
precisely so a forker with unlabelled records still has one figure to watch. That diagnostic is
**not** called the guardrail, and it is blind to the same case the guardrail is: a reply that
misreads the cancellation penalty and then judges its own misreading correctly.

`compute()` is deliberately a *different function* from `owed_commission()`. Changing who gets
chased is a policy change; changing what is owed is a definition change, and they must not be the
same edit.

## What it measures, and the number that matters most

Two models, same 55-record corpus, same judge, same guardrail — see the committed run records in
`results/` (`eval-r001-commission-audit.json`, `eval-r002-commission-audit.json`).

**Claim-validity accuracy against gold is the headline**, because whether the money is owed is the
whole question, and *not owed as claimed* is the positive class: a line the property does not owe
and pays anyway is the error that costs money. **The fast tier scored 55 of 55, with 1.00 recall and
1.00 precision on the 27 invalid claims** — including all 9 penalty-window cancellations, all 5
rebooked reservations and all 5 claims whose arithmetic is perfect on a booking that never came
through the channel. On field extraction it was exact: 770 of 770 cells, and all 440 returned values
on the nine spannable fields located back to their own section of the record. The recovery flag
fired on 16 of 16 records with no false alarms, and no reply on either tier ever disagreed with its
own numbers.

**The deliberating tier matched it on every record it answered — and answered 54 of 55.** That is
published as it ran, and the missing record is worth more than the score:

### The one thing that failed in 110 calls was this kit's own retry policy

`CMA-0013` was lost in `r002` to `<urlopen error [Errno 60] Operation timed out>`. The adapter's
retry loop already classified 429 and 5xx as transient and retried them; a connection that never
completes raises a bare `URLError` that `except urllib.error.HTTPError` never sees, so it propagated
on the first attempt and the harness recorded a lost document. It returned no completion and was
billed for nothing — which is the same reasoning the 503 path already used. The classification was
missing, not the policy.

Fixed in `src/adapters/__init__.py` (a `transient` flag on `AdapterError`), and red-proved rather
than assumed: a simulated stall now gets 5 attempts, an HTTP 400 still gets exactly 1. **The run was
not re-fired to tidy the denominator.** Its headline accuracy reads 0.9818 rather than 1.0 solely
because that record is counted as *unanswered* — not as a line that needed nothing. That is why an
unknown is never a pass anywhere in this kit.

**Two tiers clearing a corpus perfectly is a real result and a small one.** It convicts the shortcut
and it cannot rank the models — the fast and deliberating tiers are separated here by 23% more
output tokens and 78% more p50 latency (4,931 ms against 8,764 ms) and by nothing else. 55 records
took 289.8 seconds of wall clock on the fast tier and 517.7 on the deliberating one, serially. See
`Business.not_good_enough` on the published kit page.

## The baseline is shipped, including where it wins and exactly where it does not

`--baseline` is a non-LLM extractor: eight fixed disputing phrases in the reviewer's note, no key,
no cost. It is very good at the parts that are regex work — **all thirteen structured fields, 715 of
715 cells, perfect**, including both nullable ones — and it is a deliberate *tone floor* on the
fourteenth: it reads the reviewer's prose and never runs the computation, which is precisely the
shortcut the prompt forbids.

It scores **60.0% claim-validity accuracy — 22 of 55 records wrong**, with 9 unowed claims called
owed and 13 valid claims called failures. Every one of those 22 is a record where the reviewer's
note is written in the register that contradicts the folio. Both model tiers got all 22 right.

Making the baseline perfect would take five branches and one multiplication over values it already
has. Not doing so is the design — the floor is the *shortcut*, and the gap it opens is the gap
between reading prose and running the arithmetic.

**And watch what happens to the guardrail downstream.** The floor extracts `invoice_status`
correctly every single time, by regex — and its recovery flag still scores only 12 of 16 with 6
false alarms, because it inherits the tone-derived validity verdict. That is the honest lesson of
shipping a business-condition guardrail: *it is only ever as good as the field it reads.*

The floor's keyword list was checked against **both** note registers before it was ever run, not
after a defect turned up live — a sibling kit in this series shipped a keyword that fired on a
negation inside an accepting note and mis-registered four records for days. `evals/check_labels.py`
asserts that property here for free, before any run may spend: every note template must classify to
the register it was authored in.

## There is no LLM judge in this kit

The gold is exact and an answer is one value, so `==` (with light normalisation) settles it — and
the validity verdict is arithmetic, which is the one thing you should never ask a model to
adjudicate. Adding an LLM judge would add cost and a second source of disagreement to a computation
that does not need one.

## The four layers

| layer | where |
|---|---|
| minimal UI | `src/app.py`, `ui/` — one file, one call, on your machine |
| pipeline | `src/segment.py` (addressable sections) → `src/select.py` (which sections per field) |
| AI layer | `src/prompt.py`, `src/extract.py`, `src/adapters/` — one provider, one key |
| eval layer | `evals/run.py`, `evals/judge.py`, `evals/baseline.py`, `evals/check_labels.py` |

`src/select.py` exists for the same reason it exists in every sibling extraction kit here: sending
fourteen fields × the whole record is fourteen times the input tokens of sending each field the
section that could possibly state it. **The bill is driven by the context, not by the question** —
on the worked example the system prompt and field schema are 1,532 of 1,785 input tokens (86%) and
the claim record itself is 253.

The saving is usually invisible, because the sections that get sent would have been sent anyway.
Here there is one you can point at: **`Property` is mapped by no field at all**, so the union of the
mapped sections leaves it out and it never reaches the provider. And note what `SECTION_HINTS` maps
`claim_valid` to — the eight folio facts the rule actually reads, and **not** the reviewer note, and
**not** the non-room charges. The note reaches the model anyway, as a field in its own right, so
that is not a filter hiding the decoy; it is the map of where the answer actually lives. Leaving the
tax line out is the sharper choice of the two: the base is defined by what it *excludes*, and naming
the excluded thing as evidence about validity is an invitation to use it.

### `MAX_TOKENS` is a measurement, not a guess

`evals/max_tokens.py` fired three records at a deliberately generous 8,000-token ceiling before
anything else spent: **294, 540 and 746 output tokens**, all stopping on their own, none clipped
(`results/tokens-c000-commission-audit.json`). The spread is the finding, not the median — a 2.5×
range on a fourteen-key JSON object whose keys never change means whatever produces the extra 450
tokens is not the record. A ceiling set near the middle would clip the tail, and a clipped reply is
not a short reply, it is an unparseable one. `MAX_TOKENS = 4000` is ~5.4× the largest measured.

### Spans are searched inside the field's own sections first, and money is formatted before the search

`src/extract.py::_locate()` looks for a value in the sections `select.py` maps the field to, and
only falls back to the whole document. Four money figures sit on one folio here and a claimed
commission can share digits with a refund or a penalty, so a document-wide search can cite the wrong
section for a value that is genuinely correct. A citation that looks checkable and is wrong is worse
than none at all.

`_span_value()` is the other half: the model returns bare numbers and the document states them
formatted (`52.23 USD`, `15.0 pct`), so the value is rendered the way the corpus writes it *before*
searching. A bare `52.23` locates; a bare `52.2` would not, and a correct value would have shipped
with no span.

## Two defects found by opening the page, not by a gate

**The field-table counter printed `8 OF 7 WITH A SPAN`** on the very first live screenshot.
`room_revenue_usd` is exactly `0` on a cancellation or no-show, and `0` is falsy in JavaScript — so
the denominator dropped a field the numerator had counted. No structural check can see that; opening
the page can. Every count in `ui/app.js` now asks whether a value was *stated*, never whether it is
truthy.

**And the near-miss property name above.** Both were caught by looking at what shipped rather than
at what passed.

## Point it at your own claim lines

Replace `data/corpus/*.txt`, write your own `data/fields.json`, and supply a gold record per claim
line. `SECTION_HINTS` in `src/select.py` maps fields to section headings and **will** need editing
for a different statement layout; when it does not match, selection falls back to the whole document
— slower, more expensive, always correct. The commission structure in `owed_commission()` is
invented for this corpus and resembles no real agreement; replace it, and `compute()` with it,
before you chase anything real by them.

If your claim lines are unlabelled — the normal case — the field grade, the confusion matrix and the
recovery flag's score all go away. What does not go away is the consistency diagnostic, and that is
the one figure you can compute on day one.

## What it does not do

**It assumes the folio join, and that is the biggest thing between this kit and a real
reconciliation.** Every record arrives with the claim line already matched to the right folio. In
production, finding that folio is the expensive half — a channel's confirmation number against a
property system that renumbered it, or against a rebooked reservation carrying a different number
entirely. This kit does not search for a folio; it reads one it was handed.

It never short-pays an invoice, raises a dispute, credits an account or contacts a channel, and it
is not a substitute for a settlement process. The guardrail reads two fields out of the reply: if
the model misreads the cancellation penalty and then judges that misreading consistently, the line
is routed — or not routed — on a wrong number, and nothing here re-reads the document to catch it.
It knows nothing about what a variance is worth. It reads one claim, one folio and one currency, so
a stay billed across two invoices, a group block claimed as one line, a rate that changed
mid-contract, or a conversion between the channel's currency and the property's is out of scope and
unmeasured. No OCR — a real channel statement arrives as a spreadsheet or a rendered PDF, and
neither extracts text here.

**No red-team run exists for this kit.** The reviewer's note is free text and is the field an
indirect prompt injection would arrive in, which makes it the obvious place to attack; three of the
four security boundaries this kit names hold on evidence, and that fourth one is named as open
rather than quietly counted as safe. In a real deployment there is a second surface this corpus does
not model at all: the claim line itself is authored by the channel, while every character here was
written by `tools/build_corpus.py`.

No auth, no database, no multi-tenancy, no deployment story. It runs once per model, locally, and
that run is what gets published.
