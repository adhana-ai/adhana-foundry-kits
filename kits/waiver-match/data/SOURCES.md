# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every progress-payment package from a
fixed seed (`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no
third-party data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `waiver-match-2026-08-22-55packages` |
| licence | **MIT** — this repository's own licence |
| packages | 55, in `data/corpus/*.txt`, 104,931 bytes |
| parties inside them | 225, across 3–5 tiers per package |
| gold | 55 rows in `data/gold.jsonl` |
| projects / contractors / suppliers / waiver numbers | all invented, with no link to a real project, a real company, a real filed notice or a real waiver |

## ⚠︎ What this kit is not

**It is not legal advice and it does not determine anybody's lien rights.** It assembles the
coverage picture behind one progress payment and names every gap in it. A person decides whether
to release the payment.

**No jurisdiction's statutory waiver form is reproduced.** Lien waiver requirements vary by
jurisdiction, and several places prescribe the exact form of a waiver by statute. This corpus is
modelled on the general **structure** those forms share — a named party, an amount, a
through-date, and the conditional/unconditional and progress/final distinctions — and reproduces
no state's statutory text, no filed preliminary notice and no real waiver document.

**The coverage rule below is this kit's own invention.** It is five conditions in a fixed order,
chosen because it is the smallest rule that is genuinely useful and readable off one package.
It is not any jurisdiction's law and it is not any general contractor's release policy.

## Why an invented set of payment packages, when real ones exist

**Because a real lien-waiver payment package is not something this repo can publish either.** It
names a real project, real subcontractors and suppliers with real amounts owed to them, and a
payment coordinator's own note about a live commercial dispute. There is no public corpus of
(payment package, correct coverage picture) pairs, for the same reason there is no public corpus
of bank statements or proof-of-delivery records.

Every party name, project name, waiver number, subcontract number, amount, date and coordinator
note here was invented for this corpus. **No real person's data appears anywhere in it.**

## The mechanic: one call per package, eleven fields

Each package states an identifier, a project, the general contractor, the subcontract reference,
the pay application number, the period-through date, the total being released, whether the prior
progress payment has cleared, whether the application is scheduled or on hold, a **Waiver
Coverage** block listing three to five parties with their tier, the amount due to each, any
preliminary notice on file, the waiver on file with its type, amount, through-date and signing
date, and whether that party is on a joint check — and finally the payment coordinator's own
free-text note.

The model extracts eleven fields — everything except the prime contractor and the subcontract
reference, which no field maps to and which are therefore never sent (see `src/select.py`) —
including the three it has to work out: how many parties are uncovered, which is the first, and
why.

## The rule, and the priority order a reader working fast gets wrong

```
For EACH party, in document order, stop at the FIRST condition that is true:

  1. no_waiver_on_file   no waiver on file for this party
  2. notice_after_waiver the party's preliminary notice is dated AFTER the waiver was
                         signed -- the waiver predates the claim it would have to reach
  3. period_short        a PROGRESS waiver whose through-date is earlier than the
                         package's Period Through date.  A FINAL waiver has no
                         through-date and can never be period_short
  4. amount_short        the waiver amount is less than that party's amount due
  5. conditional_stale   the waiver is CONDITIONAL and something has already cleared
                         against it: Prior Payment Cleared is yes, OR that party is on
                         a joint check, which clears on issue
  otherwise              covered
```

Four things about that rule are stated to the model in full, because each is a reading a careful
person still falls into:

| | |
|---|---|
| **a notice dated after the waiver outranks everything below it** | the waiver can be unconditional, for the full amount, covering the whole period — and still not reach a claim asserted after it was signed. Every check a fast reader runs says covered |
| **a final waiver can never be short on period** | it reaches all work through completion, so its through-date is written `n/a` — and a reader mechanically comparing dates finds no date and calls it a gap |
| **period outranks amount** | a waiver for twice the amount due whose through-date stops inside the period is `period_short`, not covered and not `amount_short` |
| **a joint check clears on issue** | both payees negotiate it, so a conditional waiver on a joint-check party is already spent **even when the package says the prior payment has not cleared**. It is the one case where the package-level answer is not the answer |

The rule lives in one function — `tools/build_corpus.py::coverage_status()` and
`src/extract.py::coverage_status()` are the same five-condition logic, used to write gold and
available to re-check it — and is stated to the model by `src/prompt.py` and `data/fields.json`,
so the kit cannot drift about what "covered" means.

## The planted ambiguity: coverage is arithmetic, and the coordinator's note disagrees with it

`N_AMBIGUOUS = 22` puts a payment-coordinator note from the wrong register on exactly 40% of
packages:

- a package with a genuinely uncovered party carrying a settled note — "All waivers received and
  filed, nothing outstanding on this one." — while the party blocks say otherwise;
- a fully covered package carrying a note that reads like a live problem — "Waiver file looked
  thin on this one -- escalated for a second pass before release."

Gold is **never** derived from the note. It is the coverage rule, run party by party over the same
values the package itself states.

`evals/check_labels.py` re-runs that rule over every gold row before a run is allowed to spend and
fails if any label disagrees with its own values — and separately asserts the four sharp cases
above directly against `src/extract.py::coverage_status()`, plus that every note template
classifies to the register it was written as, against the free floor's own keyword list, before
anything may spend. Two obvious keyword candidates here, "complete" and "looked", appear in **both**
registers on this corpus ("it looked complete" is settled; "Not confident the waiver coverage is
complete" is not), so both were rejected before the floor was first run rather than after a defect
was found live.

## The composition is exact, then shuffled — not drawn per package

Each class here is a fixed **count**, shuffled by the seeded RNG, rather than drawn from an
independent coin per package. A sibling kit in this series asked for 40% ambiguity and delivered
51% on its first version; a count 1.7 standard deviations off its own design is sampling noise
being published as a corpus property. The corpus is still deterministic and still byte-identical
on every run; what changes is that the numbers below are the numbers the design asked for.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` routes a package back to the coordinator when at least one party is
uncovered **and** the application is scheduled to be released this cycle. A package with a gap
that is already on hold is not news — somebody has stopped it. The same gap on one scheduled to go
out is the package that has to be pulled back today, before the money moves.

⚠︎ **This is the kit's own simplification, not any contractor's release policy and not a legal
test.** No jurisdiction's statute, no filed subcontract and no real payment procedure was
consulted, and none is reproduced. A real payment desk weighs the dollar size of the exposure, how
far down the tiers the gap sits, whether a bond covers it and what the subcontract says about
withholding; this is two values and an AND, chosen because it is the smallest rule that is
genuinely useful and readable off one reply.

⚠︎ **It routes, it does not authorise.** A package with no gap is not thereby cleared for release
— it is a package this kit found nothing to say about.

## What it cannot tell you

⚠︎ **This kit assembles and flags only — it never releases a payment, withholds one, files a
notice or contacts a party.** `parties_uncovered` is an extracted answer and `needs_hold` is a
routing signal; nothing here disposes of anything.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real waiver
file carries confusions this one does not attempt — a waiver signed by somebody without authority,
a party that appears under two spellings across two documents, retainage released separately from
the progress amount, a bonded job where the waiver question is different in kind, a waiver whose
amount is stated in words as well as figures and the two disagree, or a preliminary notice served
on the wrong party. A model that clears this corpus has cleared what this corpus tests, not every
way waiver coverage can go wrong.

⚠︎ **Every package here is plain text with one consistent layout.** Real waivers arrive as scanned
PDFs, photographs of signed paper, and exports from four different project-management systems.
There is no OCR step in this kit.
