# Where this corpus came from

**It was written here.** `tools/build_corpus.py` generates every QC pack from a fixed seed
(`SEED = 20260822`), so the corpus is byte-identical on every rebuild and there is no third-party
data in this kit at all.

| | |
|---|---|
| source | generated by `tools/build_corpus.py`, seed `20260822` |
| dataset version | `ctr-precheck-2026-08-22-56packs` |
| licence | **MIT** — this repository's own licence |
| packs | 56, in `data/corpus/*.txt`, 89,588 bytes |
| gold | 56 rows in `data/gold.jsonl`, 14 fields each |
| filing rulebook | `data/rulebook.json` — **written for this kit**, see the warning below |
| patrons / properties / records / notes | invented names built from syllables, invented property names, invented record and reference numbers, invented preparer notes, with no link to any real person, casino, gaming operator, property or filing |

## ⚠︎ The rulebook is invented and is NOT an authority

**`data/rulebook.json` was authored for this kit.** It reproduces **no** real reporting regulation,
**no** real filing form or form number, **no** filing instruction, **no** supervisory guidance and
**no** gaming operator's own compliance manual. Nothing in it was copied from, derived from, or
checked against any such document, because none was consulted.

Every number in it is a number this kit made up:

| | |
|---|---|
| threshold | **more than 7,500 CU**, for one patron, one direction, one gaming day |
| unit | **CU** — an invented unit of account. It is not a currency and it maps to no currency |
| aggregation window | a **gaming day** running **06:00 to 06:00** the following calendar date |
| staleness horizon | identification captured more than **400 days** before the gaming day |
| identification elements | a list of **five**, spelled the way this kit spells them |
| transaction codes | **twelve** invented code names, four of them non-reportable |
| same-person link keys | date of birth **and** identification reference, both |

**No real casino, gaming operator, resort, regulator, agency, form number or regulation is named
anywhere in this kit.** The property names (`Northgate Floor`, `Harbour Level`, `Riverside
Concourse`, `Old Mill Floor`, `Longview Terrace`, `Stonebridge Concourse`) are constructed compound
nouns. Patron names are built mechanically from a syllable list plus an initial — `K. Garsbourne`,
`T. Wendmere` — so a patron in this corpus cannot coincide with a real person's record by anything
but accident. Record numbers, identification references, patron account numbers, filing identifiers
and transaction identifiers are all invented formats.

The rulebook is a small, deliberately readable construction whose only job is to make the *check
shape* measurable: aggregate the qualifying entries under a stated window, link the records that are
one person, hold the required identification elements, code each entry to what actually happened,
and file only when the threshold is genuinely crossed. Several of its simplifications are visibly
not how a real programme works, and the file names them — most obviously that a filing carries
exactly one direction and one gaming day, that identity is settled by two keys and nothing else, and
that a pack carries at most one defect.

**The real authority for any filing is your own compliance programme, the filing instructions that
actually apply to you, and a qualified compliance officer's judgement.** This kit proposes a
worklist with its reasoning and names what it could not determine. **It never files anything and
never clears anything**, and nothing in it writes, transmits, lodges, approves, signs or closes
anything. That sentence is on the kit's own UI, above the answer, and not only here.

## Why an invented set of QC packs, when real ones exist

**Because a real currency-transaction filing pack is not something this repo can publish, and would
not be publishable by anybody.** It names a real patron, their date of birth, their address, their
identification document and every cash movement they made in a day, beside a real property's cage
log. There is no public corpus of (draft filing, correct defect list) pairs, and there never will
be, for reasons that have nothing to do with effort.

Generating it also makes the label mechanical: gold's `defects_found` is
`src/rulebook.py::assess()` run over the same structured values the generator itself decided, never
somebody's reading of the preparer's note.

## The mechanic: one call per pack, fourteen fields

Each pack states a draft filing — its identifier, the patron record, the gaming day, the direction,
the window it says it applied, the total it reports, the transactions it includes with their codes,
and the patron identification block — followed by the **cage transaction log** it was prepared from,
any **other patron records** appearing in that log with their link keys, and the **preparer's own
note**. The model extracts fourteen fields, including the one it has to decide: the defect list. The
`Property And Shift` section is mapped by no field and is therefore never sent. See `src/prompt.py`.

**The rulebook is sent with every call.** A threshold, a window and a code table this kit invented
are not things a model can look up, and `src/prompt.py::rulebook_block()` renders
`data/rulebook.json` into the prompt rather than restating it in prose, so the instructions and the
gold labels cannot drift apart about the same table. Measured token-for-token on the worked example:
**1,083 of 3,439 input tokens (31 pct) are the rulebook**.

## The rule, and the stopping order a reader gets wrong

```
assess(drafted_total, qualifying_total, window, linked_record, includes_linked,
       missing_elements, captured_on, gaming_day, miscoded_ids):
    qualifying total cannot be computed        -> insufficient_information   (stop)
    qualifying total <= threshold              -> threshold_not_crossed      (stop)
    window is not the gaming day               -> window_misapplied
    else linked record exists and is excluded  -> identity_split
    else qualifying > drafted                  -> missed_aggregation
    then, independently:                       -> identification_gap, type_miscode
```

Five things about that rule are stated to the model in full, because each is a reading a careless
reader falls into on its own — and each is measured on this corpus rather than asserted:

| | | measured here |
|---|---|---|
| **a non-reportable entry is not a missed aggregation** | wires and promotional credits sit in the log, are not currency, and are correctly absent from a drafted total. Seeing them left out and calling it a defect is the commonest false alarm available on this shape of check | **13 pieces of bait across the 18 clean packs** |
| **the gaming day is not the calendar day** | 06:00 to 06:00, so 02:40 the following morning is *in* and 03:15 on the day's own date is *out* | **11 out-of-window entries across the clean packs, plus 6 packs where the draft got the window wrong** |
| **one named cause per difference** | three defects surface as "the drafted total is too low", and a checker with no stopping order reports one difference three times | **19 packs where the qualifying total differs from the drafted one** |
| **a clean filing is `none`** | a QC pass that manufactures a finding to look thorough costs a person the time to clear a row that never needed clearing | **18 clean packs — the false-alarm rate's whole denominator** |
| **the preparer's note is a field to copy, not evidence** | a confident sign-off does not make a defective filing clean, and an anxious one does not make a clean filing defective | **22 packs (39 pct) whose note contradicts the answer** |

The rule lives in one function — `src/rulebook.py::assess()` — used to write gold, stated to the
model by `src/prompt.py`, and re-run over the model's own reply by `evals/judge.py`. Three readers,
one definition, so the corpus, the prompt and the diagnostic cannot drift about what a defect means.

## The planted ambiguity: the answer is a rulebook pass, and the preparer disagrees with it

`N_AMBIGUOUS = 22` puts a preparer's note from the wrong register on exactly 39 pct of packs:

- a defective filing carrying a confident sign-off — *"Reviewed against the log line by line;
  totals agree and the pack is ready to go."*;
- a filing with nothing wrong with it carrying a note that reads as though something is —
  *"Not confident the totals tie out — please re-add these before this goes anywhere."*

Gold's `defects_found` is **never** derived from the note. It is the rulebook pass, run over the same
values the pack itself states.

`evals/check_labels.py` re-runs that pass over every gold row before a run is allowed to spend, and
fails if any label disagrees with its own values — and separately asserts that every note template
classifies to the register it was written as, against the free floor's own keyword list, before
anything may spend. A sibling kit earlier in this series shipped a keyword that fired on a negation
inside a relaxed note and mis-registered four records for days; that check is written into this
kit's gate from the start rather than found live.

## The composition is exact, then shuffled — not drawn per pack

Each of the eight buckets is a fixed **count**, shuffled by the seeded RNG, and every constructor is
asserted against the rulebook at build time — a constructor that quietly stops producing its own
bucket is exactly the defect an exact composition exists to prevent.

| | |
|---|---|
| **clean — no defect at all** | **18** |
| — of those, carrying a linked record the draft CORRECTLY aggregated | 4 |
| `missed_aggregation` | 7 |
| `identification_gap` | 7 (4 a missing element, 3 stale identification) |
| `window_misapplied` | 6 |
| `identity_split` | 6 |
| `type_miscode` | 6 |
| `threshold_not_crossed` | 3 |
| `insufficient_information` | 3 |
| preparer note from the contradicting register | 22 (39 pct) |
| packs needing the totals recomputed — the pure-code flag | 25 |

**`clean` is the biggest bucket on purpose.** It is the denominator of the false-alarm rate, which is
the number this kit leads with, and a false-alarm rate over six rows moves 17 points per row and is
not a number anybody should quote. 18 rows means one false alarm moves it 5.6 points and no further.
`evals/check_labels.py` enforces a floor of 12 on it, and separately asserts that **every clean pack
carries at least one entry the draft correctly left out** — a clean pack whose log holds nothing but
the entries on the draft is a pack no checker could get wrong, and eighteen of those would publish a
flattering zero that says nothing at all.

## The guardrail is a business condition, not a check on the model

`src/extract.py::compute()` raises `needs_recompute` when the defect list contains anything that
changes **what would be filed** — a total that is wrong, a window that gathered the wrong entries, a
person split across two records, a filing that should not exist at all, or a record nobody can
compute a total from. A missing address element or a mis-coded transaction is corrected in place on
the draft and the numbers still stand; an under-reported total goes back to the preparer and
everything downstream of it is done again. `insufficient_information` counts here too — treating a
record nobody can compute a total from as though it were clean is the one thing a pre-check must
never do.

⚠︎ **This is the kit's own simplification, not any compliance programme's triage policy.** No
programme, filing instruction or supervisory guidance was consulted, and none is reproduced. A real
desk weighs how close to the deadline the filing is, whether the patron is already under review, how
large the shortfall is, and who has authority to send a pack back.

## What it cannot tell you

⚠︎ **This kit pre-checks and proposes only — it files nothing, clears nothing and contacts nobody.**
`defects_found` is an extracted field and `needs_recompute` is a routing signal; nothing here
disposes of anything, and nothing in it runs unattended.

⚠︎ **A run that scores perfectly has agreed with `data/rulebook.json`, which is a much smaller claim
than being right about a real filing.** The graders measure whether the run applied the shipped
rulebook. They cannot measure whether the rulebook is correct, because the rulebook is this kit's
own construction and no compliance officer has looked at it.

⚠︎ **AT MOST ONE DEFECT PER PACK, AND A REAL QUEUE IS NOT LIKE THAT.** The composition seeds exactly
one seeded defect per pack so that defect recall, defect precision and the false-alarm rate are
unambiguous. A real draft carries three problems at once — a stale identification *and* an
under-aggregated total *and* a mis-coded entry — and how this kit behaves when defects interact is
completely unmeasured.

⚠︎ **An invented corpus contains the ambiguity we thought to plant and no others.** A real filing
queue carries confusions this one does not attempt: a patron record duplicated by a typo rather than
deliberately, so the link keys nearly match; a name-only near-match with a different date of birth;
a transaction voided and re-entered under a new identifier; a cage log spanning a system cutover with
two identifier formats in it; amounts written with decimals and thousands separators rather than as
plain integers; and a patron whose activity crosses two properties on the same gaming day. A model
that clears this corpus has cleared what this corpus tests, not every way a filing QC pass can go
wrong.
